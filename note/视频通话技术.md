# 视频通话技术方案与学习路径

> 定位：面向本项目的接入设计，不是已实现功能说明。本次只输出方案，不修改客户端、服务、协议或数据库实现。现有项目支持私聊与文本群聊；本方案先落地一对一语音、视频通话，多人通话给出独立扩展路线。
>
> 推荐：Qt Widgets 保留聊天界面，桌面端切换到 MSVC Qt kit，用 Qt WebEngine 承载 WebRTC 页面；新增 Node.js + WebSocket 信令服务 RTCService；Linux 公网节点部署 coturn。账号体系复用 ChatServer，媒体不经过 ChatServer 或 ResourceServer。

## 1. 先说结论：采用什么，不采用什么

### 1.1 推荐组合

| 层次 | 选择 | 为什么 |
| --- | --- | --- |
| 桌面聊天与通话控制 | Qt 6 Widgets | 复用现有聊天窗口、好友和私聊会话，不重写整个客户端 |
| 音视频采集、编解码和传输 | Qt WebEngine 中的浏览器 WebRTC API | Chromium 已提供采集、回声消除、拥塞控制、加密、同步和渲染，避免自己拼装音视频协议栈 |
| Qt 与页面通信 | QWebChannel | 传控制命令、一次性接入票据、状态；不传视频帧和音频 PCM |
| 呼叫及 SDP/ICE 信令 | 独立 RTCService：Node.js、ws、gRPC 客户端 | 参考教程容易复现；与当前小包 TCP 协议隔离；业务状态只有一个权威来源 |
| NAT 穿透 | coturn：STUN + TURN | 能直连就直连，不能直连就中继；公网接入必须验证 TURN |
| 身份和权限 | 已登录 ChatServer 会话 + 短时一次性 RTC 票据 | 不再建一套用户密码，也不把聊天 token 直接交给网页 |
| 通话瞬态状态 | 单实例 RTCService 内存；Redis 保存短时票据 | 第一阶段部署简单，明确不支持 RTCService 无缝故障迁移 |
| 通话记录 | 可选独立 MySQL 通话记录表 | 只保存参与者、结果和时间，不保存 SDP、ICE 或媒体 |

第一阶段范围：私聊一对一；语音呼叫、视频呼叫、接听、拒绝、取消、挂断、忙线、无人接听、静音、关闭摄像头、设备异常提示、断线后的有限恢复。

不纳入第一阶段：群视频、录制、美颜、后台屏幕共享、移动端。它们不是“多加几个按钮”，会改变媒体拓扑、权限或设备生命周期。

### 1.2 不建议自己实现的部分

不要把音视频当作“每帧图片 + TCP 上传”来做，也不要让 ResourceServer 分片传输实时媒体。可靠有序的文件传输目标，与允许部分丢包、优先保持低延迟的实时通话不同。

FFmpeg 能编解码，Qt Multimedia 能采集/播放，但二者都不是完整的 WebRTC 通话栈。手工组合还要承担 RTP/RTCP、抖动缓冲、音画同步、AEC、ICE、DTLS-SRTP、拥塞控制等工作。学习媒体底层可以单独做实验，不作为本项目的第一条接入路线。

## 2. 项目实际约束：不能直接照抄网页示例

以下是本次查阅仓库得到的事实：

| 现状与证据 | 对接入方案的影响 |
| --- | --- |
| [README](../README.md) 描述 Qt 6 桌面端、C++ GateServer/StatusServer/ChatServer1/2、Redis、MySQL 和 Node.js 验证码服务 | 复用登录、好友和私聊关系；RTCService 是新增组件，不替换已有聊天链路 |
| [客户端 CMake](../chat_app%20desktop/CMakeLists.txt) 当前只依赖 Core、Widgets、Network、Sql | WebEngineWidgets、WebChannel 尚未接入，不能把方案当成现成能力 |
| 本地桌面构建缓存指向 Qt 6.8.3 `mingw_64` 和 MinGW g++ | Qt 官方明确 WebEngine 不支持 MinGW；推荐路线必须先迁移桌面 Qt kit 到 MSVC，不是直接加一个链接库 |
| [TcpMgr](../chat_app%20desktop/tcpmgr.h) 使用 QTcpSocket | 不能把当前聊天 TCP 当作已加密通道；敏感 RTC 票据走这条通道前必须完成传输加密 |
| [TcpFrameParser](../ChatServer1/include/TcpFrameParser.h) 校验包体 `body_length <= MAX_LENGTH`，[const.h](../ChatServer1/include/const.h) 定义其为 2048 | 生产收包包体上限为 2 KiB，SDP 可能超过它。const.h 中“总包 2048、包体 2044”的注释与解析器有差异，本方案以解析器行为为准，不扩容聊天协议 |
| [proto/message.proto](../proto/message.proto) 已有 StatusService、ChatService 与跨服通知接口 | 可以新增内部身份/权限核验 RPC，但不能宣称已经有 RTC 接口 |
| 现有聊天服务通过 Redis 在线路由与 gRPC 跨服协作 | A、B 分别连接 ChatServer1/2 时，也应能通话；RTCService 统一信令连接，不依赖两人位于同一聊天服 |

> 本机 CMakeCache 是环境证据，不是应该提交的配置。迁移 kit 时新建独立 MSVC 构建目录，不复用 MinGW 的对象文件、库或 CMake 缓存。

### 2.1 为什么另建 WSS，而不全部复用 TCP

WebRTC 没有规定必须使用 WebSocket；如果已有安全、容量足够的消息通道，也可以交换 SDP/ICE。

本项目选择 WSS 的具体理由是：当前 TCP 包体较小；浏览器不能直接使用原生聊天 TCP；独立信令服务能复用参考教程，并把呼叫状态与媒体协商集中管理。成本是多维护一个服务和一条长连接。

聊天 TCP 第一阶段只增加短票据请求/响应，不传 SDP、ICE、媒体。不要同时让 ChatServer 和 RTCService 各维护一份呼叫状态，否则接听、取消、断线时会出现双重裁决。

## 3. 两份参考资料怎么使用

本次通过浏览器读取了两篇文章的正文。第一篇是 coturn 安装、端口与 Trickle ICE 验证；第二篇是 Express + ws、两人房间、ready、offer/answer/ICE、断开清理，并明确列出了未鉴权、无房间权限和无重连等限制。页面中的部分配置及完整源码块未取得可核验的文本，本文不声称逐行审计了其完整实现。

| 参考文章 | 可以保留 | 接入本项目必须调整 |
| --- | --- | --- |
| [webrtc 的 coturn 服务搭建](https://www.yuque.com/lianlianfengchen-cvvh2/dz8xhn/cv1breif97u8agd1) | STUN/TURN 概念、公网部署、开放中继端口、查看 relay 候选 | 不沿用公开演示账号、密码或 IP；改成短时凭证、配额和 TLS；不能承诺 TURN 100% 连通 |
| [WebRTC 1v1 视频通话技术方案（Node.js + WebSocket）](https://www.yuque.com/lianlianfengchen-cvvh2/dz8xhn/gh8ft9aiy6alem34) | 信令与媒体分离，先用两浏览器复现，ws 转发 SDP/ICE | 不允许知道 roomId 就入会；改成已登录身份、指定双方、通话状态机和一次性票据 |

需要纠正的几个容易误解的说法：

- STUN 返回的是 NAT 映射候选地址，不等于保证打洞成功。ICE 实际探测并选择可用候选对。
- TURN 也受防火墙、代理、TLS 校验、出口规则和服务器可用性影响，不是“解决所有网络问题”。
- “信令服务器不传媒体”是对的；“只有 SFU 才会经过服务器”不准确，TURN 也会中继媒体，但不负责选择订阅、混流或转码。
- 5349/TCP 通常用于 TURN over TLS；5349/UDP 对应的是 DTLS 方向，不应都称作 TLS。本方案不要求开 DTLS 监听。
- 教程的两人 `Map<roomId, Set<ws>>` 适合验证协议，不足以直接承担好友呼叫、互踢和权限控制。

## 4. 选型对比：有没有更好的路线

### 4.1 桌面媒体引擎

| 路线 | 优点 | 代价/风险 | 建议 |
| --- | --- | --- | --- |
| Qt WebEngine + WebRTC JS | 与教程及官方示例一致，少量 Qt 桥接即可接入 | 桌面端迁移 MSVC；安装包增加 Chromium 相关文件；页面权限、生命周期必须管理 | 本项目以学习和一对一功能为目标时首选 |
| 保留 MinGW，外部浏览器打开通话网页 | 不迁移 Qt kit，先验证真实设备和公网链路 | 通话窗口分离；浏览器与 Qt 退出/互踢同步困难；需安全的一次性登录交接 | 学习验证或明确接受独立窗口的交付路线，不等同于内嵌体验 |
| 原生 libwebrtc + Qt 渲染 | 原生 UI、自定义媒体处理能力强 | GN/Ninja 构建、ABI、线程、采集和渲染接入复杂；升级成本高；不能假设存在稳定官方 Qt SDK | 有原生媒体工程需求再选择，不作为入门路线 |
| 商业 RTC Windows SDK | 厂商承担部分网络覆盖、运维和设备适配工作 | 费用、平台/编译器支持、数据合规、供应商锁定 | 上线时限或通话 SLA 优先于底层学习时更合适，先验证实际 Windows/Qt 支持 |

推荐方案包含桌面 kit 迁移这一实质成本。若要求“必须保持现有 MinGW + 必须内嵌”，不要硬链接 MSVC WebEngine；应重新选择独立进程媒体宿主或支持目标 ABI 的 RTC SDK，并重新做集成验证。

### 4.2 服务端媒体拓扑

| 路线 | 适合场景 | 注意事项 |
| --- | --- | --- |
| WebRTC P2P + coturn | 一对一语音/视频，学习信令与网络穿透 | 自建呼叫业务与恢复；TURN 比例决定中继成本；直连会向对端暴露网络地址信息 |
| LiveKit 等 SFU | 多人会议、统一房间/订阅管理、需要较完整 SDK 生态 | 增加媒体服务运维和带宽；本项目仍需处理好友邀请与权限；不能只换 URL 就完成迁移 |
| 托管 RTC | 面向公网产品，运维资源有限 | 按用户分钟/流量等计费，具体以厂商当期报价为准；核对区域与隐私要求 |

如果从一开始就确定主要目标是多人会议，直接采用 SFU + JS SDK + Qt WebEngine 更合理，不必先把多人 Mesh 做成生产版本。LiveKit 的官方部署文档还提供集成 TURN 路线；采用它时重新规划 TURN 归属，不默认重复部署 coturn。

## 5. 推荐架构与边界

```text
Qt 客户端 A                                      Qt 客户端 B
├─ Widgets / TcpMgr                              ├─ Widgets / TcpMgr
│    │ TLS 聊天连接                               │    │ TLS 聊天连接
│    v                                           │    v
│  ChatServer1 ---- StatusServer / Redis / MySQL -- ChatServer2
│    │ 签发短时 RTC 票据                           │
│    └──────────── 内网 gRPC 核验身份/权限 ──────────┐
│                                                 │
└─ WebEngine 页面 ─────── WSS ───────> RTCService <─┴─ WSS ── 页面
        │                           呼叫状态、SDP/ICE           │
        └────────────── WebRTC 媒体直连 ───────────────────────┘
        └────────────── 必要时经 coturn 中继 ───────────────────┘

HTTPS 页面：rtc.example.com          TURN：turn.example.com
```

图中的 TLS 聊天连接、RTCService、票据和 RTC RPC 都是拟新增能力，不是当前运行拓扑。

### 5.1 各组件只做一类事

- Qt：聊天窗口、来电通知、用户操作、一次性票据获取、登出/互踢时立即关闭媒体。
- WebEngine 页面：唯一媒体所有者；持有 MediaStream、RTCPeerConnection、RTC WSS；把来电、状态和错误通过 QWebChannel 发给 Qt。
- ChatServer：证明当前在线账号会话仍有效，验证私聊双方与呼叫权限；不处理媒体，也不裁决呼叫状态。
- RTCService：唯一呼叫状态权威；已鉴权 uid 到 RTC 连接的映射、忙线、邀请、接听、协商转发、超时、结束清理。
- Redis：一次性票据、过期时间；不把现有 `uip_<uid>` 当作 RTC 连接存在的证明。
- coturn：STUN/TURN；不认证好友关系，不维护呼叫状态，不写聊天消息。
- MySQL：原有账号/关系数据；若启用通话记录，再保存终态记录。ResourceServer 不变。

第一阶段只运行一个 RTCService 实例。进程重启时终止活跃通话、客户端提示服务中断并允许重新发起；不承诺“断线无感”。这比一开始伪装成分布式房间服务更容易维护。

### 5.2 来电为什么不能等打开通话窗口才收到

登录成功后就创建一个专用 RTC 页面和 WSS 连接，但不采集设备、不创建媒体连接。页面收到邀请后通过桥接通知 Qt，Qt 展示来电窗口；用户接听后再申请摄像头/麦克风。

这个页面不能跟随每次切换聊天对象而销毁，也不能因隐藏被置为 Discarded。需要验证目标 Qt 版本下隐藏页面的计时与后台行为；服务端用 WS ping/pong 检测连接，不能只依赖网页定时器。

用户只登录聊天但 RTC WSS 尚未认证完成，视为“通话服务未就绪”，不是可以收到来电。聊天界面必须能区分这两种在线状态。

## 6. 身份、权限与安全接入

### 6.1 一次性票据流程

1. Qt 已通过现有登录链路建立有效 ChatServer 会话。
2. Qt 通过受 TLS 保护的聊天连接发送 `RTC_TICKET_REQ`。服务端身份取自连接绑定 uid，不信任请求体中的 uid。
3. ChatServer 生成密码学安全随机 ticket，Redis 只保存其哈希及 `{uid, chat_server, session_id, expires_at}`，建议有效期 60 秒。
4. Qt 收到 `RTC_TICKET_RSP`，通过 QWebChannel 交给受信任页面。不给页面密码或长期聊天 token。
5. 页面连上 `wss://rtc.example.com/ws`，在首条 `rtc.auth` 消息提交 ticket。未认证连接 5 秒内未完成就关闭，不能收发呼叫信令。
6. RTCService 原子消费 ticket，避免并发重放；通过内网 RPC `ValidateRtcSession` 验证当前 ChatServer 上 uid 与 session_id 仍是有效在线会话。校验失败就拒绝，票据已经消费也不回滚，客户端重新申请。
7. 成功后将 WSS 固定绑定到 uid 和聊天 session_id；后续消息不接受客户端自报的发送者身份。断线重连必须申请新 ticket。

`session_id` 的当前生成实现不应直接充当可猜测与否的安全凭证；它这里只是会话标识。ticket 必须单独使用 CSPRNG 生成。

> 当前 TcpMgr 是 QTcpSocket。仅 RTC 页面 HTTPS/WSS，并不能保护经过明文聊天 TCP 的票据。公网发布的前置工作包括客户端 QSslSocket 与 Asio TLS 对应接入、服务器证书校验，以及现有登录 HTTP 的 HTTPS 化；不能用忽略证书错误替代。

### 6.2 呼叫授权

发起 `call.invite` 时，RTCService 调用拟新增内部 RPC `AuthorizeRtcCall`，核验：

- caller 仍是当前已登录会话；目标是有效账号，不是自己。
- `thread_id` 是有效私聊，双方就是该私聊参与者；按产品要求检查有效好友关系。
- 被叫有已鉴权 RTC 连接。现有聊天在线状态只是辅助显示，不能替代此条件。
- 两个 uid 都未占用其他活跃呼叫。

权限 RPC 异步返回后，还必须重新检查连接代次、双方会话与忙线状态，再在 RTCService 的同步临界区同时占用双方并创建 call。不能在 `await` 前检查空闲、`await` 后直接创建，否则两个邀请会同时通过。

所有 SDP、answer、ICE、挂断都依据连接身份与 call 成员关系定向发送，不能由 `to_uid` 或可猜测 roomId 决定任意转发。

### 6.3 登出、重复登录和失效

- Qt 收到现有离线/互踢事件，或主动退出：先停止所有 track、关闭 PeerConnection 和 RTC WSS，再释放页面。
- ChatServer 会话失效时，将拟新增 `RevokeRtcSession` RPC 发给 RTCService，参数绑定旧 session_id，不能误伤新登录会话。
- 推送撤销不是唯一保障：RTCService 建议每 5 秒核验活跃 RTC 身份，并在新邀请/接听时即时核验；核验失败或超过期限未能证明有效，按失败关闭。周期参数属于设计初值，需按规模测量。
- 撤销内部通知失败不能阻止聊天退出；允许有限撤销延迟，由周期核验兜底，文档与 UI 明确这个窗口。

服务之间使用私网 ACL 与可信调用身份，公网不暴露 Redis、MySQL 或这些 RPC。网页 Origin 白名单只是额外防线，不是账号鉴权。

### 6.4 页面与媒体安全

只加载自有 HTTPS 通话页面，QWebChannel 不注入第三方内容；拦截非白名单导航与新窗口。为页面设置 CSP，限制脚本及 `connect-src` 到自身 RTC 端点，桥接只暴露必要的通话接口。

本地联调可以使用 `http://localhost`；不要推断任意局域网 HTTP 地址或 `qrc://` 页面都能获得相同设备权限。生产方案统一用 HTTPS 稳定 origin。

摄像头和麦克风必须经过用户授权。Qt 6.8 使用 `QWebEnginePage::permissionRequested` 与 `QWebEnginePermission::grant/deny`，核对 origin、权限类型和当前用户动作后再授权；还要考虑 Windows 系统隐私设置。不能向所有网页自动 grant。

WebRTC 媒体采用 DTLS-SRTP；TURN 中继并不意味着 coturn 得到明文音视频。若未来换成 SFU，普通 WebRTC 传输加密不自动等于参与者之间的端到端加密，需要另行设计 E2EE。

如果产品不希望通话双方获知对方网络地址，可选择 `iceTransportPolicy: "relay"` 强制中继；代价是更高服务器带宽和时延，需要在隐私策略中说明。

## 7. 呼叫协议与状态机

### 7.1 标识、消息与限额

区分三个概念：`thread_id` 是长期私聊会话；`call_id` 是本次呼叫的随机唯一标识；`connection_epoch` 是本次 RTC 连接代次。不能把 thread_id 直接当成可任意进入的房间号。

`thread_id` 在现有项目属于 uint64。在 JSON、QWebChannel 与 JS 中使用十进制字符串，避免 Number 超过安全整数范围丢精度。

| 语义消息 | 发起者与职责 |
| --- | --- |
| `rtc.auth` / `rtc.auth_result` | 页面鉴权；服务端返回 RTC 身份与就绪结果 |
| `call.invite` / `call.invite_result` | caller 申请呼叫，服务端授权、分配 call_id 或返回 offline/busy/forbidden |
| `call.incoming` | 服务端向指定 callee 推送来电 |
| `call.accept` / `call.reject` | 仅 callee 能接听或拒绝 |
| `call.cancel` | caller 在未接通时取消 |
| `call.ready` | 服务端确认接听并分配 initial offerer 与 polite 角色 |
| `webrtc.description` | 两端交换 offer/answer |
| `webrtc.ice` | Trickle ICE，包括本轮候选结束标记 |
| `call.media_ready` | 每端报告媒体连接建立；不是仅收到 answer |
| `call.resume` / `call.snapshot` | 重连后核验原 call 并恢复控制状态，不自动重新创建呼叫 |
| `call.hangup` / `call.ended` | 结束申请与服务端权威终态，携带明确原因 |

建议消息外层字段：`type`、`request_id`、`call_id`（创建前没有）、`connection_epoch`、`payload`。状态事件另带递增 `state_version`，客户端忽略旧版本。`request_id` 用于应用幂等，不是媒体帧序号。

建议的初始限额：单条 WSS JSON 消息 64 KiB、SDP 字段 32 KiB、单条候选 4 KiB，每通话每协商代最多 256 条候选；禁止二进制媒体消息。限额是拟定值，用真实浏览器数据验证后调整，不是协议标准值。

超过限额明确返回错误或关闭违规连接；设置连接发送缓冲上限和消息速率限制，不能任意堆积内存，也不能静默丢掉 SDP。ws 关闭不必要的压缩，先保证信令路径简单。

描述消息示例，数值较大的 thread_id 使用字符串：

```json
{
  "type": "call.invite",
  "request_id": "b065c1d8-c6b3-4f1d-aaf2-b406054a9e95",
  "connection_epoch": "current-connection",
  "payload": {
    "peer_uid": 2002,
    "thread_id": "9007199254740993",
    "media": "video"
  }
}
```

此处 connection_epoch 只关联服务端已分配的当前连接，不是鉴权凭证；发送者 uid 始终由 WSS 绑定身份取得。

### 7.2 服务端权威状态

```text
INVITING ──callee accept──> CONNECTING ──双方 media_ready──> ACTIVE
   │                            │                             │
   ├─reject/cancel/timeout───────┤                             │
   └─offline/permission error───┴──media failed/hangup──────────┤
                                                              v
                                                            ENDED
```

Qt 显示状态可以包含 Idle、Outgoing、Incoming、Connecting、Active、Reconnecting、Ended，但必须服从 RTCService 的 call_id 与 state_version。UI 状态不能替代服务端状态机。

关键规则：

- 同一 uid 同时只参加一个非终态 call，包括响铃阶段。
- accept 与 cancel 同时发生：按 RTCService 实际提交的顺序裁决。cancel 已终结则 accept 返回 call_ended；accept 已进入 CONNECTING，则 caller 的 cancel 按结束呼叫处理，不能把它悄悄丢掉。
- 双方同时呼叫：第一个成功占用双方的 call 生效，另一个请求返回 busy，并包含可关联的已存在呼叫状态；不能创建两个独立呼叫。
- 重复 request_id 返回同一结果；断线后用 snapshot 查终态。ENDED 不得因迟到 accept、SDP 或 ICE 再次激活。
- 初始建议响铃超时 30 秒、接听后建连超时 20 秒；这都是服务端期限，不依赖页面定时器。
- 没收到 answer 不等于被叫未接听；接听与媒体建连是两阶段。
- 终态记录短时保留，例如 5 分钟，支持幂等结束与状态查询；随后清理。双方 uid 占用只在归属仍为该 call_id 时释放。

### 7.3 正常呼叫流程

```text
A/Qt+页面           RTCService            ChatServer             B/Qt+页面
   │ call.invite        │                     │                       │
   │───────────────────>│ AuthorizeRtcCall    │                       │
   │                    │────────────────────>│                       │
   │                    │<────────────────────│                       │
   │ invite_result      │ 原子占用A/B         │                       │
   │<───────────────────│ call.incoming ─────────────────────────────>│
   │                    │<────────────────────────────── call.accept │
   │<── call.ready ─────│─────────────────────────────── call.ready >│
   │ 申请本地设备       │                     │         申请本地设备 │
   │ offer ────────────>│────────────────────────────────────────────>│
   │<───────────────────│<──────────────────────────────────── answer │
   │<───────────────────│──────────── 双向 trickle ICE ─────────────>│
   │<══════════════════════ P2P / TURN 音视频 ════════════════════════>│
   │ media_ready ──────>│<────────────────────────────── media_ready │
   │<── ACTIVE ─────────│─────────────────────────────────── ACTIVE >│
   │ hangup ───────────>│────────────────────────────────── call.ended│
   │<── call.ended ─────│                     │                       │
```

caller 可在主动发起时先做本地设备预检；callee 只能在用户接听后申请设备。任何一侧失败或用户一直不处理权限弹窗，都必须有可取消和期限，不能永远停在 CONNECTING。

## 8. WebRTC 媒体协商与设备行为

### 8.1 先理解这条链

```text
getUserMedia → MediaStreamTrack → addTrack
            → offer/answer 协商 → ICE 选路 → DTLS-SRTP → ontrack 播放
```

- SDP 描述媒体、编解码、传输参数，不是视频内容。
- ICE candidate 是可能的网络路径，不是对方账号身份。
- Trickle ICE 表示发现候选后增量发送，不等待全部收集结束才发送 SDP。
- initial offerer 由 call.ready 指定；两端协商逻辑仍按 perfect negotiation 设计，以处理后续重新协商的 offer 碰撞。

### 8.2 必须处理的协商边界

1. 每个 call 创建自己的 PeerConnection，不能复用已关闭实例给下一次通话。
2. 收到 ICE 时若 remoteDescription 尚未设置，按 call_id 和协商代缓存；设置成功后按顺序提交。失败和结束时清空缓存。
3. 通过 polite/impolite、makingOffer、ignoreOffer 与 remote answer pending 处理 offer glare，参考 MDN perfect negotiation；业务上的同时呼叫忙线与 WebRTC offer 碰撞是两件事。
4. ICE 关联到协商代及 ICE ufrag。旧轮候选不能加入重启后的新会话；被忽略 offer 对应的候选也要忽略。
5. 正确处理候选收集结束标记，不把 null 当成普通候选字符串；不要无差别吞掉 addIceCandidate 错误。
6. 按 call 串行处理协商消息。传输有序不代表异步 setRemoteDescription 回调也有序完成。
7. ontrack 按 track/stream 绑定远端播放器；不能假设每个事件都带有非空 streams。

### 8.3 首批媒体参数与控制

| 项目 | 建议 |
| --- | --- |
| 语音呼叫 | `audio: true, video: false`，不要申请摄像头权限 |
| 视频呼叫 | 初始使用 640×360 或 640×480、约 24～30 fps 的 ideal 约束；不以 exact 强制筛掉旧摄像头 |
| 音频 | 开启/请求 echoCancellation、noiseSuppression、autoGainControl，实际效果在目标设备测量；耳机是基础回声排查手段 |
| 编解码 | 首先验证共同支持的 Opus + VP8；不要假设 Qt 包内 H.264 已启用或具有发行许可 |
| 本地预览 | muted，避免自己声音回放；远端音频不能同步静音 |
| 自动播放 | 处理 `video.play()` 被拒绝，提供用户点击播放入口，不能只看到图像就判定声音正常 |
| 静音 | 切换音频 track.enabled，不重新建立 call；对方 UI 状态由控制事件同步 |
| 关闭摄像头 | 仅 enabled=false 不承诺释放设备。若按钮语义为“停止采集”，detach/replaceTrack(null) 后 stop 本地视频 track；恢复时重新采集并 replaceTrack，需要时重新协商 |
| 切换设备 | 接通后先采集新 track、成功替换再停止旧 track；失败保留旧设备，给出可见错误 |

视频设备不可用时，不静默把视频呼叫变成语音。提示用户，并通过双方确认的媒体模式变更降级；麦克风不可用时提供明确失败原因。

### 8.4 生命周期是重点，不只是画面能出来

Qt 6.8 的设备权限属于非持久权限，不能假设“第一次授权后永远不用处理”。处理拒绝、NotFoundError、NotReadableError、OverconstrainedError 和长时间不回复授权。

用户挂断/退出、页面崩溃或窗口关闭时：停止所有本地 track → 关闭 PeerConnection → 清除候选、计时器和播放器 srcObject → 发送结束/关闭 WSS（按退出场景）→ 释放页面。后台异步 getUserMedia 若在结束后才返回，也必须立即 stop 新拿到的 track。

通话窗口右上角关闭要有明确语义：第一阶段按挂断处理，最小化才保留通话。不能窗口消失但麦克风仍然持续上传。

## 9. 网络故障与恢复

“聊天连接断了”“RTC WSS 断了”“媒体 ICE 失败”不能混为同一个状态。

| 故障 | 处理策略 |
| --- | --- |
| 聊天会话退出/被踢 | 不恢复旧 call；本地立即停止媒体，RTCService 撤销旧会话 |
| WSS 临时断开，媒体尚通 | 显示控制连接中断，最多给 10 秒恢复窗口；本地挂断随时有效，即使发不出 hangup |
| WSS 恢复 | 从仍有效的聊天会话获取新 ticket，重新认证、提交 call.resume；服务端校验成员/代次/期限并返回 snapshot，不能重放 invite 创建新 call |
| WSS 未在期限内恢复 | 服务端结束 call，通知仍在线对端；本地 watchdog 也停止媒体，不能无限通话 |
| ICE disconnected | 可为短时网络抖动，先观察约 5 秒，不立即建第二条呼叫 |
| ICE failed 或网络切换持续失败 | 在控制连接有效且双方仍授权的前提下，取得新 TURN 配置、setConfiguration、restartIce，重新协商；初期每次故障最多一次重启，约 15 秒恢复失败则结束 |
| RTCService 重启 | 当前通话不迁移；两端重连后找不到活跃 call，统一结束并由用户重新发起 |
| coturn 中断 | 直连通话可能不受影响；中继通话可能失败。多 TURN 节点只提高新选路机会，不代表已有 allocation 能迁移 |

这些超时是起始参数，不是网络成功率承诺。重连期间仍会收到迟到的旧连接回调，所有回调应检查 call_id、connection_epoch 和页面生命周期代次。

单实例服务内 busy 映射与 call 终态必须一次性清理；只删除房间、不释放 uid 占用会造成永久忙线。进程崩溃后的历史记录可以在下次启动时把未终结记录收敛为 service_interrupted，不能标成“正常结束”。

## 10. coturn 部署与凭证

### 10.1 部署顺序

建议使用带稳定公网地址的 Linux 云主机。Windows 客户端不意味着 TURN 也应部署在开发机；WSL 可以学习命令，但不能代替公网 NAT 与防火墙验收。

Ubuntu/Debian 包安装示例：

```bash
sudo apt update
sudo apt install coturn
turnserver --version
```

配置前备份原有配置；发行版包的服务启用方式以本机 unit 为准。不要直接在生产机器覆盖原有 turnserver.conf。

### 10.2 配置模板

以下是配置说明模板，必须替换域名、IP、secret 与证书路径后才能启动；不是仓库已经部署的配置。`use-auth-secret` 启用基于共享密钥的时限凭证机制，不再同时保留教程的静态 `user=` 或 `no-auth`。

```ini
listening-port=3478
tls-listening-port=5349
fingerprint
realm=turn.example.com
use-auth-secret
static-auth-secret=REPLACE_WITH_SERVER_ONLY_RANDOM_SECRET

# 云主机公网地址映射到私网网卡时设置；直接持有公网IP时按拓扑调整。
# 映射必须保持中继端口可达，不能仅转发3478。
external-ip=PUBLIC_IP/PRIVATE_IP

# 显式限制中继范围；容量不足时扩容并同步调整安全组。
min-port=49152
max-port=49999

cert=/etc/letsencrypt/live/turn.example.com/fullchain.pem
pkey=/etc/letsencrypt/live/turn.example.com/privkey.pem
no-tlsv1
no-tlsv1_1

# 本方案使用UDP relay，仍允许客户端经TCP/TLS连接TURN。
# no-tcp-relay不是禁止TURN客户端的TCP监听。
no-tcp-relay
no-multicast-peers

# 起始配额，按真实allocation数量与业务预算调整。
user-quota=4
total-quota=500
log-file=stdout
```

还要配置部署环境对应的 denied-peer-ip 规则，禁止向 loopback、链路本地、私网/云元数据地址等敏感目标中继，覆盖实际启用的 IPv4/IPv6。不要启用 allow-loopback-peers 或 server-relay；不要暴露管理端口。证书私钥仅允许必要服务用户读取，续期后按发行版支持方式重新加载/重启。

端口与容量关系取决于 allocation、地址族、TURN 节点数量和实现配置，不能把中继端口数量直接当作可支持通话人数。小范围是学习初值，需要用真实中继并发测量。

### 10.3 对外端口

| 端口/协议 | 用途 | 开放要求 |
| --- | --- | --- |
| 443/TCP，RTC 域名 | HTTPS 页面与 WSS | 反向代理到私网/本机 RTCService；支持 WebSocket Upgrade |
| 3478/UDP、3478/TCP | STUN/TURN | 云安全组与主机防火墙同时放行 |
| 5349/TCP | TURN over TLS | 提供可信证书，客户端配置 `turns:` |
| 49152～49999/UDP | 本模板的媒体中继端口 | 与 min-port/max-port 完全一致；还要检查出站和 NAT 映射 |
| 443/TCP，独立 TURN IP（可选） | 严格网络的 TURN/TLS 备用入口 | 需额外监听/端口映射或 L4 代理；不能让普通 HTTPS location 反代 TURN |

不要为 TURN 直接套 HTTP 反向代理。TLS 443 对某些受限网络有帮助，但使用显式 HTTP 代理、深度过滤或严格出口策略时依然可能失败。

### 10.4 动态凭证

RTCService 只向已授权 call 的参与者发放 TURN 凭证，共享 secret 保留在 RTCService 与 coturn，不进入 JS、安装包或仓库。

```text
expires_at = Unix时间秒 + 600
username   = "expires_at:uid"
credential = Base64(HMAC-SHA1(shared_secret, username))
```

这就是 coturn TURN REST 风格的凭证计算。初始有效期建议 10 分钟；不是“10 分钟后必然挂断”：已建立 allocation 的行为与实现及会话刷新有关。长通话与网络切换时必须能够重新发放凭证，不能假设旧凭证永久适用于新 allocation。

可以在到期前获取并设置新 iceServers，必要时在既定恢复逻辑内重新协商；凭证更新不是每到期一次就无条件中断通话。同步服务端与 TURN 时钟。

注意 `username` 中放 call_id 也不会让 coturn 自动理解 call 成员权限，且每次生成不同 username 会削弱按用户名配额的效果。应用侧另按 uid 限制发证速率与活跃呼叫数，coturn 配置总体 allocation/带宽限制。

浏览器接入结构：

```javascript
const pc = new RTCPeerConnection({
  iceServers: [
    { urls: "stun:turn.example.com:3478" },
    {
      urls: [
        "turn:turn.example.com:3478?transport=udp",
        "turn:turn.example.com:3478?transport=tcp",
        "turns:turn.example.com:5349?transport=tcp"
      ],
      username: turnConfig.username,
      credential: turnConfig.credential
    }
  ],
  iceTransportPolicy: "all"
});
```

`turnConfig` 是服务端向当前已授权通话返回的短时配置，不是前端自己计算的 secret。

### 10.5 怎么证明 TURN 真的工作

1. 用 [Trickle ICE](https://webrtc.github.io/samples/src/content/peerconnection/trickle-ice/) 填入自己签发的短时凭证，出现 relay 候选。不要填写参考文章公开的账号。
2. 两台异网设备将 `iceTransportPolicy` 改为 `relay` 做双向实际语音、视频通话。
3. 用 `getStats()` 核对实际选中的 candidate-pair，并观察 bytesSent/bytesReceived 持续增长。只有出现 relay 候选不证明媒体可通。
4. 分别只配置 TURN/UDP、TURN/TCP、TURN/TLS 验证对应路径；测试客户端禁 UDP 场景，而不是只在服务器看监听端口。
5. 测试错误/过期凭证不能创建新 allocation，证书异常能被拒绝；coturn 日志初始 401 challenge 可能是正常认证流程，不能看到一个 401 就判定失败。

```cmake
    Qt6::WebEngineWidgets Qt6::WebChannel)
```

这是采用 Qt 6.8 权限 API 的最低版本选择。安装对应 MSVC 64 位 kit 的模块，确认平台运行库一致；在新构建目录配置。不要把“从源码构建整个 WebEngine”的 Node/Python 等工具要求，误写成使用预编译 WebEngine 包的全部依赖。

分发时除 Qt DLL 外，还包括 QtWebEngineProcess、resources、locales、平台插件及 MSVC 运行库。优先用 Qt 部署工具/现有部署脚本覆盖，再在没有开发环境的干净 Windows 机器启动验证。

第一阶段通话记录不是前置条件。若需要记录，建议独立 `rtc_call` 表：call_id 主键、thread_id、caller_uid、callee_uid、media、created_at、accepted_at、connected_at、ended_at、end_reason。时间由服务端产生；connected_at 在双方 media_ready 后写入；同一 call_id 终态写入幂等。历史记录失败不能阻止即时挂断与资源释放。

不要直接给现有 chat_message 塞一个未定义的“通话类型”：若要求在聊天气泡展示通话结果，需要同步消息类型、服务器存储、历史同步、Qt渲染和SQLite结构，另做完整契约迁移。

## 13. 验收矩阵与排障

### 13.1 必须实际跑的场景

| 分类 | 场景 | 预期观察 |
| --- | --- | --- |
| 正常功能 | A视频呼叫B，接听、静音、摄像头关闭/恢复、挂断；再做纯语音 | 双向媒体与UI一致；语音不索取摄像头；挂断设备释放 |
| 跨服 | A登录ChatServer1，B登录ChatServer2 | RTC呼叫成功，不要求同聊天服 |
| 授权 | 非好友/非私聊成员、伪造caller、猜call_id、票据过期与重放 | 被拒绝；没有收到别人的SDP或ICE，也没有发放TURN配置 |
| 状态竞争 | 同时互拨、接听与取消同时发生、重复挂断、迟到ICE | 只有一条权威call，无状态复活、无永久busy |
| 设备 | 拒绝权限、忽略权限弹窗、摄像头被占用、拔掉设备、播放策略拒绝 | 可见错误和可取消状态；异步回调不重新打开已结束call |
| 生命周期 | 窗口关闭、最小化、页面崩溃、登出、被另一端登录踢下线 | 按定义结束或保留；退出与互踢立即停止本地采集 |
| 网络 | 异网、强制relay、禁UDP、Wi-Fi切热点、WSS断连/恢复 | 观察实际选路，恢复成功或在期限内明确结束 |
| 服务故障 | RTCService重启、coturn停机、身份RPC超时 | 不假装正常连通；fail closed；无无限重试与无限采集 |
| 资源 | 连续100次建立/挂断与反复来电取消 | 设备可再打开；页面、PeerConnection、服务房间/uid占用和进程内存无持续增长趋势 |
| 发布 | 不带开发工具的Windows机器运行安装包 | WebEngine进程、插件、证书、媒体权限与声音正常 |

界面看见视频还不够：耳机/扬声器分别验证双向声音，确认不是只播放了本地预览；测试结束检查摄像头灯及麦克风采集状态。

### 13.2 起始性能目标，不能当作测量结果

可先设：接听且双方设备授权完成后，正常网络建连耗时 P95 不超过 5 秒；720p作为后续质量档；一对一通话体验的端到端延迟目标约 300 ms 内。是否达到必须在指定网络、设备和样本数下测量，本次没有进行实际通话，不能给出达标结论。

`getStats()` 可提供 RTT、丢包、抖动、收发码率、帧率、丢帧与选路。RTT不是端到端音画延迟；后者可用拍摄计时器或音频回环实验估算。

### 13.3 排障顺序

1. Qt kit与WebEngine模块是否正确，发行包中的QtWebEngineProcess是否能启动。
2. 页面是否HTTPS、安全origin与桥接是否就绪，系统/页面权限是否允许设备。
3. RTC票据是否成功消费并核验，双方RTC连接是否都在线。
4. call是否进入CONNECTING，offer/answer是否对应当前协商代，ICE是否过早/过期。
5. getStats实际选中的candidate-pair是什么；relay候选存在但不通时检查中继端口、external-ip、TLS与出口规则。
6. bytesReceived增长但无声音/图像时再查播放器、track状态、设备、自动播放和编解码。

生产日志只记录 request_id、call_id、必要身份标识、状态迁移、错误分类和聚合网络指标。避免完整记录票据、聊天token、TURN凭证、SDP、ICE地址和原始媒体；开发抓包与诊断文件也要有权限和保留期限。

## 14. 容量与成本：一对一不等于服务器零成本

令每端总媒体发送码率为 b，通话时长为 T 秒，中继比例为 p。对单个TURN中继节点、单次转发每方向的典型链路：

- 一条双向中继通话的服务器出站约为 `2 × b` bit/s，入站也约为 `2 × b`。
- C条并发平均出站约 `2 × C × p × b`，再加协议开销和容量余量。
- 单次完全中继的出站量约 `2 × b × T / 8` 字节。

例：每端总发送码率1.5 Mbit/s、完全中继、10分钟，则约225 MB出站；100条全部中继的并发约300 Mbit/s出站。这里是十进制MB、估算未含开销，不是云账单报价。若链路跨两个TURN节点，应分别计算各节点/计费边界，不能套一个节点的公式。

还要预算RTCService连接数、TURN allocation、网卡、CPU、Redis与身份核验RPC压力、云公网流量和日志保留。先实测中继比例，再决定是否需要多地区节点；不要引用“单核能跑几千通话”作为本项目容量保证。

## 15. 学习路径：按产物推进，不先啃完整协议规范

下面按每周约8～12小时给出参考节奏，可以按已有知识跳过基础。完成条件比日历更重要。

| 阶段 | 要学什么 | 动手任务 | 学完应能解释/证明 |

## 16. 多人和后续演进的边界

多人Mesh中，n个人理论上需要 `n(n-1)/2` 个两两连接，每个人可能发送n-1份媒体；即使CPU允许，上行带宽也会先成为问题。不要把教程的房间人数限制改大，就宣称支持稳定群视频。

采用SFU时，客户端向SFU发布轨道、按需订阅对方轨道。仍需根据本项目thread_id和群成员权限签发房间权限，入会前与踢人/退群后重新核验；群消息权限不能自动替代持续媒体访问控制。

RTCService横向扩容也是另一项真实工程：需持久/共享的call状态、两个uid占用的原子更新、连接所在实例路由、跨实例事件投递、超时清理和故障后终态收敛。仅把Map换成Redis、或给WSS加负载均衡/粘性会话，都不能保证不同实例上的双方互通。达到单实例容量瓶颈或需要高可用时，再完整实施这一层。

录制应独立设计参与者告知/同意、存储加密、访问控制与删除期限；一对一P2P不会天然在服务器生成录像。屏幕共享需要独立用户授权、屏幕轨道结束处理和目标平台验证，不默认采集系统声音。

> 推荐执行入口：先完成“两个浏览器 + 公网TURN强制中继”的可运行实验，再完成MSVC Qt内嵌与干净机器部署；随后按票据鉴权、呼叫状态机、故障恢复顺序接入真实聊天项目。本文中的新服务、协议、超时、容量与性能都是设计建议或目标，实际支持情况以对应阶段运行证据为准。
