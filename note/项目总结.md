# 项目总结



## 项目描述

一个全栈的即时通讯项目，前端基于 `Qt` 实现气泡聊天对话框，通过 `QListWidget` 实现好友与会话列表，利用 `GridLayout` 和 `QPainter` 封装聊天气泡组件，并基于 Qt Network 封装 HTTP 和 TCP 通信。

后端采用分布式设计，分为`GateServer`网关服务，多个`ChatServer`聊天服务，`StatusServer`状态服务以及`VerifyServer`验证服务

各服务通过 `gRPC` 通信。TCP 读写错误和应用层心跳超时都会进入统一会话清理。

`GateServer`对外提供`http`服务，负责处理用户登录，注册，修改密码等功能。登录时`GateServer`从`StatusServer`查询聊天服务实现负载均衡，`ChatServer`聊天服务采用`asio`实现tcp可靠长链接异步通信和转发，采用多线程模式封装`iocontext`池提高并发性能，数据存储采用`MySQL`服务，并基于`X DevAPI`封装连接池，实现`MysqlMgr`单例，同时基于`hiredis`封装redis连接池，在数据库前做一层缓存，并且实现`grpc`连接池保证多服务并发访问

`VerifyServer`提供邮箱验证服务，使用`Node.js`编写

## 已实现功能

1. 账号注册、邮箱验证码、密码重置和 HTTP 登录；`StatusServer` 根据 Redis 在线数为用户选择 ChatServer，并签发 TCP 登录 token。
2. Qt 客户端通过 TCP 长连接完成登录、用户搜索、好友申请、好友认证、好友列表展示和文本消息收发。
3. 好友认证与显式创建私聊都会创建或复用唯一的 `chat_thread/private_chat`；认证消息与普通文本消息均写入 MySQL `chat_message`。
4. 客户端按登录 UID 创建独立 SQLite 数据库，缓存会话摘要、消息历史和同步游标；支持登录后的会话/消息增量同步，以及从本地 SQLite 上拉更早历史。
5. 同服和跨 ChatServer 的在线文本消息都携带 `message_id`、`thread_id`、收发者、创建时间和状态。接收方客户端以 `message_id` 幂等写 SQLite，并更新会话最后消息、显示时间和未读数。
6. 发送方收到服务端确认后同样把消息写入 SQLite；发送失败、回包字段不完整或本地写入失败时，客户端根据 `msgid` 在气泡旁显示 `send_fail.png`。
7. ChatServer1 与 ChatServer2 通过 Redis 保存用户路由，并使用 gRPC 转发好友认证结果和在线文本消息；跨服文本转发会原样同步完整消息元数据。
8. 同一账号重复登录时，服务端通过 Redis 路由和会话 ID 校验通知旧连接下线；客户端和服务端都实现应用层心跳与统一断线清理。

连接容量取决于机器内存、Windows socket/句柄限制、客户端临时端口、网络栈和服务负载，不能脱离测试环境给出固定结论。仓库中的 `tests/connection_capacity_test.cpp` 会同时对 `ChatServer1:8090` 和 `ChatServer2:8091` 建立并保持连接，分别输出两台实例在当前环境的实测成功连接数。



### 技术点

Asio 网络库、gRPC、Node.js、多线程并发、Redis、MySQL、SQLite、Qt 信号槽、网络编程、设计模式。



## 考察点



### 如何利用asio实现tcp服务

ChatServer 的实现分为“监听接入”和“连接读写”两层：

1. 主线程创建 `boost::asio::io_context` 和 `CServer`。`CServer` 构造时用 `tcp::acceptor` 绑定配置中的 TCP 端口，并立即调用 `StartAccept()`。
2. `StartAccept()` 从 `AsioIOServicePool` 按轮询策略取一个 `io_context`，用它创建 `CSession`；`acceptor.async_accept()` 在主 `io_context` 上异步等待新连接。接入成功后调用 `CSession::Start()`，并将 session 放入 `_sessions` 映射维持生命周期，然后继续投递下一次 `async_accept`。
3. 每个 `CSession` 先异步读固定 4 字节包头，再根据包头中的消息 ID 和包体长度读满包体。收包使用“累计读取直到长度足够”的方式，能处理 TCP 的半包和粘包；长度或消息 ID 非法时主动关闭连接。
4. 完整消息会封装为 `LogicNode`，投递给 `LogicSystem` 的业务队列。网络线程只负责 I/O，登录、好友、聊天等业务逻辑不直接阻塞 I/O 回调。
5. 发送端使用每个 session 独立的 `_send_que`。只有队列从空变为非空时才发起一次 `async_write`；写完成后再发送队首下一条，避免多次异步写交叉造成字节流乱序。队列超过 `MAX_SENDQUE` 时丢弃新消息，防止慢客户端无限占用内存。
6. 读写出错会关闭 socket 并调用 `CServer::ClearSession()`，从 `_sessions` 和用户会话映射中清理；已登录用户还会更新 Redis 中的在线计数。

关键代码：`ChatServer1/src/CServer.cpp`、`ChatServer1/src/CSession.cpp`、`ChatServer1/src/AsioIOServicePool.cpp`。`ChatServer2` 的实现相同，仅运行配置不同。

### 如何保证服务高可用

要区分当前的“可横向扩展”与完整的“高可用”。

当前实现：

1. ChatServer 可以部署多个实例。当前配置启用 `ChatServer1` 和 `ChatServer2`，分别监听 8090/8091，服务间通过 gRPC 50055/50056 转发跨服好友通知和文本消息。
2. StatusServer 从 Redis 的 `login_count` 哈希读取各实例在线人数，优先选择负载最小的实例；负载相同时轮询选择，避免所有新连接落到第一台服务。
3. 用户登录后，ChatServer 将 `uip_<uid>` 写入 Redis，记录用户当前所在实例。发送消息时可由该路由决定本机投递或跨服 gRPC 转发。
4. GateServer、StatusServer 与 ChatServer 的职责拆分，使单台 ChatServer 的扩容不会改变客户端 HTTP 登录入口。

当前不足：

1. `login_count` 只能反映已正常启动且已上报的实例，不是健康检查；实例异常退出可能留下过期路由或计数。
2. 没有服务注册中心、心跳上报、租约过期、自动摘除和故障转移。StatusServer 当前不会主动探测 ChatServer 是否可连接。
3. Redis 和 MySQL 都是单点配置，没有主从、哨兵/集群、备份恢复或跨机房方案。

若要达到生产级高可用，需要给 ChatServer 增加带 TTL 的注册/心跳与 StatusServer 健康检查，选择实例时跳过失联节点；Redis 使用 Sentinel 或 Cluster，MySQL 使用主从/高可用方案；消息先持久化或进入可靠队列，再做幂等投递与离线补偿；客户端在连接断开后使用退避重连并重新获取路由和 token。

### 为什么封装连接池，Mysql，redis？

创建数据库或 Redis 连接通常需要 TCP 建连、认证和协议协商。每个请求临时创建连接会增加延迟、频繁消耗系统资源，并且在并发高时容易把数据库连接数耗尽。连接池预先创建有限数量的可复用连接，用“借出、使用、归还”控制资源上限。

本项目的具体实现：

1. `MySqlPool` 在启动时按 `config.ini` 的 `poolsize` 创建 `mysqlx::Session`。`GetConnection()` 在空闲队列为空时通过条件变量等待；归还时唤醒一个等待者。借出与归还均由互斥锁保护。
2. MySQL 连接借出和归还时执行 `SELECT 1` 检查有效性；发现断开的 Session 时重新创建。业务代码用 `std::unique_ptr` 持有连接，并用 `Defer` 在作用域结束时归还，避免异常或提前返回时泄漏连接。
3. `RedisMgr` 也通过连接池取出 hiredis 连接，执行命令后归还。Redis 被用于验证码、登录 token、用户在线路由、各 ChatServer 在线人数和用户资料缓存，避免频繁访问 MySQL。
4. ChatServer 间的 `ChatConPool` 为每个对端服务预建 5 个 `ChatService::Stub`。跨服调用从池中借出 stub，RPC 完成后归还，从而限制并发 RPC 资源并减少重复创建 channel/stub 的开销。

连接池不是越大越好。池大小需要由数据库最大连接数、单次查询耗时、线程数和压力测试共同决定；池耗尽时当前实现会等待，因此还应为生产环境补充超时、监控和熔断策略。

### 设计模式和思想

1. 单例模式：`Singleton<T>` 管理 `MysqlMgr`、`RedisMgr`、`LogicSystem`、`UserMgr`、`AsioIOServicePool`、gRPC 客户端等进程级共享组件。构造函数私有并由模板基类创建，避免多份连接池或全局会话表。
2. RAII：连接、gRPC stub、socket 和线程分别由 `unique_ptr`、`shared_ptr`、封装类与析构函数管理。`Defer` 用于在函数返回或异常时归还 MySQL/gRPC 资源，降低遗漏释放的风险。
3. 生产者-消费者：网络会话将收到的 `LogicNode` 放入 `LogicSystem` 队列，业务线程再取出处理，使 I/O 和业务逻辑解耦。
4. Reactor/异步回调：Asio 使用 `async_accept`、异步读和异步写注册完成回调，由 `io_context::run()` 分发 I/O 事件，不需要每个连接一个阻塞线程。
5. 对象池：MySQL、Redis、gRPC stub 复用昂贵连接；`AsioIOServicePool` 复用固定数量的 I/O 线程。
6. 分层与职责分离：GateServer 面向 HTTP，StatusServer 管理路由和 token，ChatServer 管理长连接与消息路由，VarifyServer 管理邮件验证码。客户端只连接网关和分配到的 ChatServer，不直接访问中间件。
7. 缓存旁路：用户信息优先读取 Redis，未命中再访问 MySQL 并回写缓存；写操作后需要同步更新或删除相关缓存，避免陈旧数据。

### 线程池如何封装

`AsioIOServicePool` 不是传统“任务函数队列 + 工作线程”形式，而是 Asio 的 `io_context` 线程池：

1. 构造时按 `std::thread::hardware_concurrency()` 创建多个 `io_context`，并为每个 context 创建一个 `executor_work_guard`。
2. 每个 `io_context` 对应一个线程，该线程调用 `io_context::run()`，持续分发它所持有 socket 的异步完成回调。
3. `work_guard` 的作用是即使暂时没有 I/O 事件，`run()` 也不立即返回，线程池可以长期等待新连接。
4. `GetIOService()` 通过原子递增索引和取模实现 round-robin。`CServer` 接收新连接时，为该连接选择一个 context；同一 `CSession` 后续读写都在该 context 的线程上执行，减少跨线程切换和并发访问 socket 的复杂度。
5. 停止时先 `reset()` 所有 work guard，再 `stop()` 所有 context，最后 `join()` 全部线程，保证线程退出和资源回收有序。

需要注意 `hardware_concurrency()` 在极少数环境可能返回 0，生产代码应兜底为至少 1 个 I/O 线程；业务计算耗时较长时也不应直接跑在 I/O 回调中，应转交专门的业务工作线程池。

### 为什么要设计心跳

TCP 的“连接存在”不等于对端仍然可用：拔网线、进程假死、NAT/防火墙静默回收空闲连接时，双方可能长时间得不到 `read` 或 `write` 错误。心跳用于定期确认连接存活，并及时清理失效会话。

一个完整的应用层心跳通常包括：

1. 客户端按固定间隔发送心跳请求，携带协议版本、时间戳或递增序号；服务端立即回复。
2. 双方记录最后一次有效收包或心跳响应时间。连续若干周期未收到响应，则主动关闭 socket、清理本地状态。
3. 客户端关闭后采用指数退避重连；重新从 GateServer/StatusServer 获取可用 ChatServer 和新的 token，再执行 TCP 登录。
4. 服务端清理时删除 Redis 的 `uip_<uid>` 路由并修正 `login_count`，避免把新消息路由到失效会话。

Qt 客户端在 TCP 登录成功后每 20 秒发送
`1023`，60 秒未收到有效 `1024` 就主动断开；ChatServer 对 `1023` 直接回复 `1024`，并每
10 秒扫描 Session，超过 60 秒未收到完整合法 TCP 包就走统一断线清理。心跳控制帧不进入
`LogicSystem` 的业务队列，避免业务积压影响存活判断。当前仍未实现自动重连、重新获取路由
和重新登录状态机。


### 登录为什么分成 HTTP 和 TCP 两段？token 起什么作用？

完整链路：

1. Qt 的 `LoginDialog` 把 `user + xorString(passwd)` 通过 HTTP POST 到 GateServer 的 `/user_login`。GateServer 依次 `Checkuser`、`CheckPwd`，这一步是"验身份"：确认用户存在且密码正确，并拿到 uid。
2. 密码验证通过后，GateServer 通过 gRPC 调 StatusServer 的 `GetChatServer(uid)`。StatusServer 选一台负载最低的 ChatServer，生成一个随机 token，写入 Redis 的 `utoken_<uid>`，把 `{host, port, token}` 返回网关再转给客户端。
3. 客户端拿到地址后建立 TCP 长连接，发 `MSG_CHAT_LOGIN {uid, token}`。ChatServer 的 `LoginHandler` 从 Redis 读 `utoken_<uid>` 做比对（等价地也可以走 proto 里已定义的 StatusServer `Login` RPC），不匹配就回 `UidInvalid / TokenInvalid`。
4. 校验通过后才 `session->SetUserId(uid)`、加载用户资料与好友/申请列表、给 Redis 的 `login_count` 加一、写 `uip_<uid>` 并绑定到 `UserMgr`，最后回 `MSG_CHAT_LOGIN_RSP`。

为什么这样拆：

1. 密码验证是低频、一问一答的操作，适合短连接 HTTP；聊天是高频推送场景，需要 TCP 长连接。两层职责分离后，ChatServer 不需要把"用户密码是否正确"这件事重新做一遍。
2. token 是"该 uid 刚刚通过密码验证"的凭证。TCP 是一条全新通道，客户端只喊一句"我是 uid 1002"是没法信的，必须带上 token 证明自己拿到了 HTTP 登录结果；密码不会在 TCP 通道上再次出现。
3. 选择哪台 ChatServer 发生在服务端内部，客户端只拿到 `host/port`。以后加第三台、第四台 ChatServer，客户端代码不用改。

回答时要主动说的现状与缺口：

1. `utoken_` 没有设置 TTL，登录成功后也不删除、不轮换，token 泄露后到下一次登录覆盖前都有效；生产要加过期时间、一次性消费或刷新机制。
2. HTTP/TCP 都没有 TLS，`xorString` 只是混淆不是加密，README 里明确写了"教学级实现，不能当安全方案宣传"。
3. 登录回包把用户资料、好友申请、好友列表一次性带下来，优点是少一次往返，缺点是一次登录要做多次 Redis/MySQL 查询，后面的登录接口压力测试要重点看这里。

关键代码：`GateServer/src/LogicSystem.cpp`、`StatusServer/src/StatusServiceImpl.cpp`、`ChatServer1/src/LogicSystem.cpp`（`ChatServer2` 同步版本）。


### StatusServer 怎么决定把新连接分给哪台 ChatServer？在线数从哪里来？

StatusServer 的 `getChatServer()` 是"最小负载 + 轮询"：

1. 构造时解析 `config.ini` 的 `[ChatServers]`，把每台 ChatServer 的 host/port/name 放进内存 map。
2. 选服时对每台服务器 `HGet(login_count, 服务器名)` 取当前在线数。读不到或解析失败的值按"最大负载"处理，不会因为读不到数据就被当成 0 优先分配。
3. 找出负载最小的候选集合；负载相同（例如刚启动全是 0）就用 `_round_index` 轮询，避免永远偏向前一台。

在线数字的来源在 ChatServer：

1. 启动时 `HSet(login_count, 本机名, "0")`，正常退出时 `HDel`。
2. 每次 token 校验通过、`SetUserId` 成功，用 `HIncrBy(login_count, 本机名, +1)` 上报一次。
3. 会话断开时，`CServer::ClearSession` 若发现该 session 已登录（uid != 0），会 `RmvUserSession` 并 `HIncrBy(..., -1)`。

为什么放在 Redis 而不是 StatusServer 内存里：

1. StatusServer 和多台 ChatServer 是不同进程，`login_count` 是"所有进程共同要看的分布式状态"，Redis 天然提供共享存储。
2. 用 `HINCRBY` 而不是"GET 出来 +1 再 SET"，是为了避免两个请求并发登录时互相覆盖，`HINCRBY` 是 Redis 内的原子操作。
3. 今后 StatusServer 自己做多副本时，这份计数也能继续共享，不会每份各自统计。

局限要如实讲：

1. 计数是“当前登记的在线会话数”。同一 uid 正常重复登录时会先让旧服减一，再让新服加一；异常退出或路由已经陈旧时仍可能出现漂移。
2. 进程被 kill、断电、网络分区等没走正常清理路径时计数会残留；启动时重置为 0 只对"正常重启"有效。
3. 它只是负载参考，不是健康检查：StatusServer 不会主动探测 ChatServer 是否可连，异常实例的计数不会自动摘除，也没有租约过期机制。
4. 服务器列表目前靠配置文件维护，扩第三台要同步改 StatusServer 的 `[ChatServers]` 和各 ChatServer 的 `[PeerServer]`，还不是注册中心自动发现。

关键代码：`StatusServer/src/StatusServiceImpl.cpp`、`ChatServer1/src/LogicSystem.cpp`、`ChatServer1/src/CServer.cpp`、`ChatServer1/src/UserMgr.cpp`。


### 同一账号重复登录、旧连接断开的竞态问题怎么回答？

“一个账号只保留一个有效连接”的处理流程如下：

1. `LoginHandler` 获取 Redis 分布式锁 `login_lock_<uid>`，在锁内读取 `uip_<uid>`，因此同一 uid 的并发登录会串行执行。
2. 登录端同时读取 `usession_<uid>`。旧会话同服时先核对本机 session_id；跨服时把旧 session_id 放进 `KickUserReq`，旧服只踢 ID 完全匹配的会话，陈旧请求返回 `ServerBusy`。
3. 踢人 RPC 成功后才写入新 `uip_<uid>`、`usession_<uid>` 和本机 `UserMgr`。若对端不可达、连接池不存在或 3 秒 deadline 超时，新登录返回 `RPCFaild`，不会冒险覆盖旧路由。
4. `NotifyOffline` 把下线通知排入发送队列，拒绝后续业务消息；队列写完后服务端主动关闭旧 socket。Qt 客户端收到 1021 后切回登录页；若通知未完整解析，已登录连接的 `disconnected` 回调也会触发一次连接丢失退出，两条路径带去重标志。
5. 每个 ChatServer 只创建一个 `CServer`，TCP 登录与 gRPC 踢人共享同一份 `_sessions`，避免 RPC 操作到另一份空会话容器。

仍需如实说明的边界：本地映射删除与踢人 RPC 会校验 session_id，正常互踢顺序还受分布式锁保护；客户端失联会触发心跳超时清理，但 ChatServer 进程崩溃、10 秒锁租约过期等极端场景仍需 Redis 路由租约治理。Redis 的“比较 session_id + 删除 key”目前是持锁后的多条命令，生产化时可收敛成 Lua 原子操作。自动重连也尚未实现。


### 一条文本消息从用户 A 到用户 B 的完整链路是什么？可靠吗？

发送链路：

1. 客户端 `MessageTextEdit` 把输入转成若干条 `MsgInfo`，文本消息用 `QUuid::createUuid()` 生成 `msgid`；`ChatDialog` 按约 1024 字节一批组装 `textArray`，发送 `ID_TEXT_CHAT_MSG_REQ`。
2. ChatServer 的 `HandleTextMsg` 校验登录会话 UID、目标 UID 和消息数组后，创建或复用私聊会话，并在 MySQL `chat_message` 写入消息。写入成功后生成 `message_id`、`thread_id`、收发者、创建时间和状态等确认元数据。
3. 目标用户在本机时，ChatServer 直接发送带完整元数据的 `ID_NOTIFY_TEXT_CHAT_MSG_REQ`；目标用户在另一台 ChatServer 时，经 `ChatGrpcClient::NotifyTextChatMsg` 转发同一份 `TextChatData`，目标服务再生成相同的 TCP 通知。
4. 发送方收到 `ID_TEXT_CHAT_MSG_RSP` 后按 `thread_id` 聚合确认消息并写入 SQLite；接收方在 `TcpMgr` 校验实时通知的完整字段后发出 `sig_text_chat`，`ChatDialog` 将消息、会话摘要、未读数和同步游标放入同一个 SQLite 事务。

消息持久化、同步与发送状态：

1. `message_id` 是 MySQL 和 SQLite 的消息主键，用于实时通知去重、会话历史分页和登录后的增量同步；`thread_id` 用于关联私聊会话、会话摘要和同步游标。
2. `msgid` 是客户端 UUID，用于把服务端回包关联到发送前展示的乐观气泡；成功确认由 SQLite 记录重绘，失败时在气泡旁显示 `send_fail.png`。
3. 客户端按 UID 保存独立 SQLite 文件。登录后先读取本地会话与近期消息，再通过 `ID_LOAD_CHAT_THREAD_REQ/RSP` 和 `ID_LOAD_CHAT_MSG_REQ/RSP` 拉取缺失数据。
4. 聊天窗口支持从 SQLite 读取更早消息；会话列表显示最后消息、最后消息时间和未读数，实时消息和历史同步使用同一套本地存储接口。


### TCP 长连接上伪造 uid/touid 怎么办？现在的防护到哪一步？

可以分三层回答：登录关、数据校验关、权限校验关。

1. 登录关是有的：ChatServer 校验 `utoken_<uid>` 通过后才 `SetUserId`，所以裸连一个 TCP 端口、谎报 uid 登录会被 token 挡住。
2. 数据校验只做了部分：文本消息处理前检查 `session->GetUserId() == fromuid`，因此一个已登录用户没法伪造"替别人发消息"；`touid` 只是接收方，属于正常选择目标。跨服转发时也携带同样字段，由对端服务器推送。
3. 权限校验有明显缺口：
   - `UserSearchHandler` 没有要求会话先登录，任何能建立 TCP 连接的人都能按 uid/用户名查用户资料；
   - `AddFriendApply`、`AuthFriend` 把 `uid/touid/fromuid` 完全信任 body，没有绑定到 `session->GetUserId()`。攻击者登录后可以冒充别的 uid 发起好友申请，也可以替别人同意申请（只要数据库里存在对应待处理申请，事务就可能落库）；
   - 文本消息只校验了"发送者确实是 session 本人"，没有校验"双方必须是好友"，知道 uid 且对方在线就能发消息。

回答时给出修复原则：**当前用户身份一律从 session 取，body 只允许放"对方是谁"；服务器端必须再做好友关系、申请状态等业务校验；登录态、心跳、TLS、限流和幂等一起补，才谈得上安全**。


### 注册、好友申请、同意好友的数据库设计为什么这么写？

表结构设计：

1. `user` 表有自增主键 `id` 和业务号 `uid` 两个身份：物理主键短、内部自增；uid 对外暴露、可以稳定迁移，并用唯一索引约束。
2. `user_id` 是单行 uid 分配器。`RegUser` 在一个事务里执行 `UPDATE user_id SET id = id + 1` 再 `SELECT` 得到新 uid，随后带参 `INSERT INTO user`。单行 UPDATE 在 InnoDB 里天然加行锁串行化，配合事务保证"uid 分配了但用户没插进去"时整体回滚。
3. `friend` 关系按方向各存一行（`self_id/friend_id`），唯一索引 `(self_id, friend_id)` 防重复；`back` 字段保存"我给他起的备注"，所以必须拆两行才能让双方备注独立，查询好友也只需要 `WHERE self_id = ?` 再 join `user`。
4. `friend_apply` 用唯一索引 `(from_uid, to_uid)` 保证两个人之间只有一条申请记录；`status` 表示待处理/已同意（2 预留拒绝）。

同意好友为什么用事务 + 行锁：

1. `AddFriend` 先 `startTransaction`，`SELECT ... FOR UPDATE` 锁住这条申请记录再判断状态：待处理则置为同意，已经是拒绝等终态就直接回滚，避免把终态申请"复活"。
2. 然后插入两条好友记录（接收方、申请方各一条），插入用 `ON DUPLICATE KEY UPDATE back = back`，重复同意时是幂等操作不会产生重复好友。
3. 双方的 `back` 分别来自同意方本次填写的备注和申请时留下的 `applicant_remark`，最后 commit；任一步抛异常就 rollback。这样不会出现"申请已同意但好友只加了一边"。
4. 重复申请的处理用 `INSERT ... ON DUPLICATE KEY UPDATE`：待处理申请可以刷新申请备注，已是终态的申请不会被新请求覆盖。

其他面试点：

1. 所有 SQL 用 `?` + `bind()` 参数化查询防注入；`desc` 是 MySQL 保留字必须加反引号；X DevAPI 走 33060，返回列从 0 开始取。
2. 用户资料有 `unameinfo_<name>`、`ubaseinfo_<uid>` 两份 Redis 缓存，先读缓存、未命中再查 MySQL 并回填。目前改密码/改资料后没有主动删缓存，属于缓存一致性缺口；正确做法是写操作后按 key 删除或更新相关缓存。
3. 可以追问"状态存哪"：以 `friend_apply.status` 为唯一事实源，好友列表、红点都由它推导，避免两套状态不一致。

关键代码：`sql/create_tables.sql`、`ChatServer1/src/MysqlMgr.cpp`（GateServer/StatusServer 内同步版本）。


### 服务之间为什么选 gRPC？当前实现有什么性能和可靠性坑？

选择理由：

1. 所有服务共享一份 `proto/message.proto`，C++ 和 Node.js 都从同一份协议生成代码，接口即契约，改接口只改一处，不会出现两端悄悄不一致。
2. gRPC 基于 HTTP/2，支持多路复用，protobuf 是紧凑二进制，比 HTTP + JSON 更适合服务间高频内部调用；方法、消息类型都有强约束。
3. 客户端到网关用 HTTP/JSON 是因为低频且要兼容调试；服务内部跨语言、跨进程才用 gRPC，各取所长。

代码里的连接池实现：

1. GateServer 到 VarifyServer 建 `RPConPool`（5 个 stub）、到 StatusServer 建 `StatusConPool`（10 个 stub）；ChatServer 给每个对端服务建 `ChatConPool`（5 个 stub）。
2. 池用"预创建 stub + 条件变量等待 + 借出/归还"实现，和 MySQL/Redis 连接池同一套生产者-消费者思想；`Defer` 保证 RPC 结束即使中途 return 也会归还。
3. 为什么要池：限制同一时刻在途 RPC 数量、复用 channel/stub 创建成本；注意 gRPC stub 本身通常可并发使用，这里池的价值更多是"并发上限可控 + 资源复用"。

必须指出的坑：

1. 当前 RPC 都是同步 unary 调用。GateServer 的业务回调跑在 Beast 的异步 IO 回调里，里面又同步调 MySQL 和 gRPC，一个慢后端会占住该连接所在的 IO 线程，影响同池的其他请求。
2. ChatServer 的 `LogicSystem` 只有一个消费线程，登录、加好友、跨服转发里的 Redis/MySQL/同步 gRPC 全部串行执行，消息量大时队列会成为单点瓶颈。
3. gRPC 客户端目前没有 deadline/超时重试和熔断，`grpc::CreateChannel(..., InsecureChannelCredentials())` 还是明文传输；对端进程假死时调用方只能等默认超时。

生产化改进方向：GateServer 把业务丢进独立工作线程池或用异步 gRPC；LogicSystem 改成多 worker + 按 uid/session 分片队列；RPC 加 deadline、重试、熔断和链路超时；内部通信至少走 TLS/mTLS 或内网白名单。


### Qt 客户端是怎么组织网络层和界面的？聊天区为什么不用 QListWidget 直接装气泡？

网络层：

1. `HttpMgr` 和 `TcpMgr` 都是 `QObject + Singleton<T>`，用信号槽把"谁发出请求、谁处理结果"解耦：登录/注册页面向 HttpMgr 发请求，HttpMgr 收 `QNetworkReply` 后按模块发 `sig_*_mod_finish`；TcpMgr 收服务器推送后发 `sig_friend_apply / sig_auth_friend / sig_text_chat` 等，界面层订阅即可。
2. 客户端解析服务器协议：包头 `[msgid(2)] + [body len(2)]`，统一网络字节序；`readyRead` 里把数据 append 进 `_buffer`，不够一个包头就等，够了先剥离包头，再等满包体，一次 `readyRead` 可能处理多个完整包，从而解决 TCP 粘包/半包。
3. 界面切换由 `MainWindow` 用 `QStackedWidget` 管理登录/注册/找回密码/聊天页；登录成功后 `TcpMgr` 发 `sig_switch_chatdlg`，`ChatDialog` 用 `UserMgr` 里的数据刷新好友列表和申请列表。

界面实现：

1. 好友/会话列表用 `QListWidget + setItemWidget`：每个 item 塞一个自定义 widget，便于放头像、昵称、预览消息、红点；列表滚动到底触发"加载更多"用自定义事件/信号。
2. 聊天消息区不用 QListWidget，而是自绘 `ChatView`（QScrollArea + QVBoxLayout）：气泡高度随文本自动变化、要左右对齐、要自动滚底和以后的头插历史消息，QListWidget 的等宽 item 模型不适合，所以做成"内容布局 + 底部弹簧"，新气泡 `insertWidget(count()-1)` 插到弹簧前。
3. 单条消息由 `ChatItemBase`（GridLayout 摆头像/昵称/气泡，Self 和 Other 镜像）+ `BubbleFrame`（paintEvent 画气泡背景）+ `TextBubble/PictureBubble` 组合；头像用 `AvatarUtil` 先等比放大再按椭圆 `QPainterPath` 裁剪，实现圆形头像。
4. Qt 对象树负责大部分 widget 内存；`QNetworkReply` 用 `deleteLater` 回收；TcpMgr 单例要在继承顺序里先继承 QObject 并带 `Q_OBJECT`，才能使用信号槽和元对象系统。

客户端聊天页已实现 SQLite 会话缓存、登录增量同步、实时消息落库和本地历史上拉；文本消息发送前会先展示乐观气泡，收到服务端失败回包或本地持久化失败时显示发送失败图标。

### LogicSystem 已经把业务和 I/O 解耦了吗？为什么仍可能成为瓶颈？

当前 `CSession` 收到完整包后，把 `LogicNode` 放进 `LogicSystem::_msg_que`，由一个
`_worker_thread` 消费。它避免了直接在 socket 完成回调里执行 MySQL、Redis 和同步 gRPC，
但只实现了单消费者，所有用户的登录、搜索、好友和聊天业务仍然全局串行。

代码里还有一个更隐蔽的问题：`DealMsg()` 取得 `_mutex` 后，从队列取出消息并直接调用业务
回调，回调结束前没有解锁。这样一个慢 SQL 或慢 RPC 不仅阻塞后续业务，I/O 线程调用
`PostMsgToQue()` 时也会卡在同一把锁上，队列并没有完全隔离 I/O 与业务耗时。

合理的第一步改法是：只在“等待、取出、弹出节点”时持锁，取到节点后立即解锁，再执行
handler；同时给队列设置容量上限并记录队列长度和排队时间。如果改为多个 worker，不能简单
地让所有消息并行消费，否则同一用户的登录、好友认证和聊天消息可能乱序。可以按 uid 或
会话 ID 哈希到固定分片队列，让同一会话串行、不同会话并行。

面试官会继续追问：

- 多 worker 后，如何保证同一会话的消息顺序？
- 一个消息同时涉及 fromuid 和 touid 时，应该按谁分片？如何避免跨分片并发更新冲突？
- 队列满了是丢弃、阻塞 I/O、断开客户端，还是返回“系统繁忙”？为什么？



### 慢客户端一直不读数据，服务器会怎样？

每个 `CSession` 有独立 `_send_que`。第一次入队时启动 `async_write`，后续消息排队，写完一条
再写下一条，因此同一 TCP 连接上不会出现多个异步写交叉。`_send_lock` 允许业务线程和 gRPC
线程安全地向同一会话投递消息。

当前背压策略比较粗：队列超过 `MAX_SENDQUE` 后，`Send()` 直接丢弃新消息，而且返回值是
`void`，上层不知道消息已丢。判断条件还是 `size > MAX_SENDQUE`，因此队列等于上限时仍会
再插入一条，存在一个 off-by-one。队列只按消息条数限制，也没有统计总字节数；一千条小消息
和一千条接近 2 KB 的消息占用并不相同。

生产化时可以设置“消息数 + 总字节数”双水位：达到高水位先拒绝非关键推送或返回过载错误，
持续超限则关闭慢连接；降到低水位后恢复。`Send()` 应返回可观察的结果，调用方才能决定重试、
落库或通知发送者失败。

面试官会继续追问：TCP 已经有流量控制，为什么应用层还需要发送队列上限？答案是 TCP 只会
让写操作变慢，不会限制业务线程继续产生待发送对象；没有应用层上限，进程内存仍可能被慢
消费者拖垮。



### “最小连接数 + 轮询”会不会在突发登录时失效？

StatusServer 读取 Redis 的 `login_count`，选择最小值；相同最小值在候选服务器之间轮询。
这能改善稳定流量下的分配，但一次选服与 ChatServer 真正完成 TCP 登录、执行 `HINCRBY +1`
之间存在时间差。大量 HTTP 登录同时到达时，它们可能都看到同一份旧计数，被集中分配给同一
实例，这属于基于快照选择的惊群或倾斜问题。

可选改进包括：选服时先在 Redis 原子预占一个 pending 计数，TCP 登录成功后转成 active，
超时则回收；或者使用带权轮询、Power of Two Choices，并把 CPU、业务队列长度、连接池等待
时间等纳入负载，而不只看连接数。无论采用哪种方式，都必须先做健康检查，不能把“计数小”
等同于“服务器可用”。

面试官会继续追问：预占成功但客户端没有建立 TCP 怎么办？需要给 reservation 设置 TTL，
并在登录成功或超时时幂等地确认、回滚。



###  Redis 挂了以后，哪些功能应该降级，哪些必须拒绝？

Redis 在本项目里同时保存验证码、token、在线路由、服务负载和用户资料缓存。它不是单纯的
“加速层”：验证码、token 和在线路由属于正确性依赖，Redis 不可用时不能直接绕过校验继续
登录或随便选择投递目标，否则会产生身份绕过或消息错投。

可以按数据性质制定不同策略：

1. 用户基础资料缓存失败，可以回源 MySQL；回填失败只影响性能，不应伪造数据。
2. token 读取失败应 fail closed，明确返回系统依赖异常，而不是混成“用户不存在”。
3. 在线路由读取失败时，不应声称对方离线；应返回临时不可用，等待重试或可靠消息存储补偿。
4. 负载计数读取失败的实例应跳过或由健康检查决定，不能仅因为计数未知就参与正常选服。

部署层面还需要 Redis Sentinel/Cluster、连接超时、熔断和恢复探测。面试时要明确：这些是
生产化方案，当前仓库仍是单点 Redis 配置。



###  gRPC 调用失败时，业务真的能感知吗？

当前文本消息路径相对完整：`NotifyTextChatMsg` 默认以 `RPCFaild` 初始化 response，检查连接池、
空 stub 和 gRPC `Status`，并把远端 `error` 写回 TCP 回包。但好友申请和好友认证路径存在不
一致：调用点没有根据 RPC response 修改本地结果；部分客户端封装还通过 `Defer` 默认填写
`Success`，连接池里找不到目标服务器时也可能返回成功，且取 stub 后缺少统一的空指针检查。

改进时应统一一套调用模板：response 默认失败，检查目标连接池、stub、deadline、gRPC
`Status` 和业务 `error`，最后再决定是否成功；所有调用都设置 deadline，按错误类型决定是否
重试。好友申请已经入库，可以把实时通知失败当成可补偿事件；好友认证通知也需要持久化状态
或 Outbox，不能只靠一次同步 RPC。

面试官会继续追问：哪些 RPC 能自动重试？只有具备幂等语义的操作才能安全重试。通知类请求
应携带稳定业务 ID，并由接收方去重；不能因为网络超时“不知道对端是否执行”就盲目重复写库。



###  验证码系统如何防刷、防猜和防重放？

当前 VerifyServer 从 UUID 截取前 4 个十六进制字符，验证码空间约为 `16^4 = 65536`；Redis
key 的 TTL 是 180 秒，并用“key 已存在”阻止同一邮箱在 TTL 内重复发送。这能完成基础流程，
但还缺少按 IP、设备、邮箱维度的频率限制和连续输错次数限制。

当前验证码在邮件发送前写入 Redis。若邮件发送失败，key 仍会保留三分钟，用户再次请求会被
判为重复。注册或重置密码成功后也没有原子删除验证码，因此同一验证码在过期前存在被重复
使用的可能。更稳妥的做法是用 Lua 脚本或事务完成“比较验证码 + 标记已消费/删除”，并维护
失败次数；发送失败时删除本次 key，限流计数和验证码 key 分开管理。

安全边界也要如实说明：当前 HTTP、TCP 和内部 gRPC 都是明文，密码只是客户端 `xorString`
后的可逆字符串。生产环境应使用 TLS，服务端使用专门的密码哈希算法和随机盐，日志中禁止
输出密码、token 与验证码。



###  为什么数据库操作失败，接口仍可能返回成功？

面试官通常会从“你的成功响应以什么为准”继续追问。当前 GateServer 注册逻辑先把
`root["error"]` 设置为 `Success` 并写入 response，之后才调用 `RegUser()`，却没有检查其返回值。
重置密码也保存了 `UpdatePwd()` 的布尔结果，但无论结果如何都返回成功。这样数据库断开、唯一
索引冲突或事务失败时，客户端可能看到假成功。

正确原则是：先完成并确认状态变更，再构造成功响应；数据库异常映射为稳定业务错误码，同时
记录内部错误详情。注册还应依赖数据库唯一索引兜底，不能只靠“先查用户名/邮箱再插入”，因为
两个并发请求可能同时查到不存在。验证码消费和用户写入若无法放在同一数据库事务中，需要
设计可重试、补偿和幂等边界。

面试官会继续追问：HTTP 是否一定要返回非 200？业务校验失败可以使用统一 JSON 错误码并结合
合适的 4xx；依赖故障通常用 5xx。关键是传输状态和业务状态语义稳定，客户端不能靠猜。



###  服务退出时，在线状态一定能清理干净吗？

当前 ChatServer 收到退出信号后停止主 `io_context`、停止 I/O 线程池并关闭 gRPC server，正常
路径会删除本机的 `login_count` 字段。但 `CServer` 析构只是清空 `_sessions`，不会逐个调用
`RmvUserSession()`；因此 Redis 中属于本机的 `uip_<uid>` 可能残留。即使逐个删除，也要防止旧
会话把用户刚在另一台服务器建立的新路由删掉。

完整的优雅退出顺序可以是：

1. 把实例标记为 draining，StatusServer 停止分配新用户。
2. 停止 accept，等待或拒绝新的业务请求。
3. 通知客户端重连，等待发送队列在限定时间内排空。
4. 使用 `uid + session_id/route_version` 条件删除本实例拥有的在线路由。
5. 注销健康状态，关闭 gRPC、I/O 与业务 worker，超时后再强制退出。

面试官会继续追问：进程被 `kill -9` 或机器断电时没有清理机会怎么办？在线路由和服务注册要
带 TTL/租约，通过心跳续期，而不能把正确性完全寄托在析构函数上。



### 现在的日志能支持线上排障吗？

当前主要依赖 `std::cout`、`qDebug` 和 Node.js `console.log`，没有日志级别、结构化字段、trace ID、
指标和集中采集。部分代码会打印完整 HTTP body、登录 token、验证码和聊天内容，这既会泄露
敏感数据，也会让日志量随业务量快速增长。

至少应补充：

- 请求级 `trace_id`，跨 GateServer、StatusServer、ChatServer 与 VerifyServer 透传。
- 消息级 `msgid`、from/to server、错误码与耗时，用户标识按规则脱敏。
- 业务队列长度/等待时间、连接池使用率/等待时间、RPC P95/P99、失败率、在线计数漂移、发送
  队列丢弃数等指标。
- 密码、token、验证码不落日志；聊天正文按隐私策略默认不记录。

面试官会继续追问“一条跨服消息失败怎么查”：先用 msgid/trace_id 串起客户端发送、源
ChatServer 路由、gRPC 调用、目标 ChatServer 推送和发送方回包，再看每段耗时和错误码，而不是
去五个控制台窗口里搜索模糊文本。



### 连接容量测试证明了服务器有多高并发吗？

仓库的 `connection_capacity_test` 会向 8090、8091 交替建立并保持空闲 TCP 连接，直到首次
失败或到达探测上限。它能证明当前机器和配置下“能接受并保持多少空闲 socket”，也能暴露
客户端临时端口、句柄或网络缓冲耗尽，但不能证明登录 QPS、消息吞吐、业务延迟或稳定在线人数。

原因是测试连接后不登录、不发消息，建连还是单线程逐次进行；没有覆盖 MySQL/Redis/gRPC、
业务队列、发送队列和 Qt 客户端处理能力。如果测试先撞到 Windows 客户端临时端口上限，结果
甚至不是服务端容量上限。

更完整的测试矩阵应包括：

1. 协议测试：拆分包头/包体、多个粘包、非法长度、未知消息 ID。
2. 链路测试：注册、登录、同服/跨服好友和聊天，以及错误回包。
3. 负载测试：并发登录 QPS、消息吞吐、P50/P95/P99、CPU、内存和队列长度。
4. 稳定性测试：长时间连接、慢客户端、频繁断连、Redis/gRPC 故障注入和服务重启。

面试官要求“项目支持多少并发”时，应给测试环境、负载模型、持续时间、成功率和资源占用；
只有一个连接数不能直接写成“支持高并发消息”。



###  自定义 TCP 协议以后怎么升级？

当前包头只有 2 字节消息 ID 和 2 字节消息体长度，正文为 JSON；服务端限制 ID 和正文长度不
超过 `MAX_LENGTH`，客户端与服务端都使用大端序。这套协议简单、便于调试，但没有 magic、
协议版本、压缩标志、校验字段和能力协商。

升级时可以在登录握手中携带客户端版本和支持能力，服务端维护一段兼容窗口；新增消息 ID 时
旧客户端应收到明确的“不支持”错误，不能直接失去响应。若修改包头，必须通过版本或 magic
区分新旧格式。gRPC protobuf 则应保持已发布字段编号和类型不变，删除字段后用 `reserved`
保留编号，避免新字段误用旧编号。

面试官会继续追问：为什么 TCP 正文用 JSON、内部 RPC 用 protobuf？当前选择偏向客户端调试
和 Qt 解析方便，内部服务则需要强契约与紧凑传输。若性能测试证明 JSON 成为瓶颈，再评估统一
protobuf；没有数据前不应只凭感觉重写协议。



### 异步回调中的 CSession 为什么不会提前析构？有没有新的生命周期风险？

`CServer::_sessions` 用 `shared_ptr` 保存活动会话，读写回调也捕获 `shared_from_this()`，保证
异步操作完成前 `CSession` 存活；`CSession` 到 `CServer` 使用原始指针，避免形成双向
`shared_ptr` 环。发生读写错误时，`ClearSession(session_id)` 在 map 中只处理仍存在的会话，
重复错误回调不会重复扣减在线数。

需要继续防守的点是：原始 `_server` 指针要求 CServer 生命周期严格长于所有会话回调；停服时
若对象销毁顺序改变，就可能出现回调访问失效 server。可以通过明确的 shutdown 协议、让 server
拥有共享状态并给 session 保存 `weak_ptr`，或把清理操作投递到 server 自己的 executor 来约束。

面试官还可能问是否需要 strand。当前一个 CSession 的读链始终在创建它的同一个 `io_context`
上串行继续，发送队列又由 `_send_lock` 保护；如果以后让同一 `io_context` 跑多个线程，或增加
更多会修改 session 状态的异步操作，应使用 strand 或统一投递，避免仅靠零散 mutex 维护状态。



### 增加到几十台 ChatServer 时，当前跨服拓扑有什么问题？

目前服务器列表来自静态 `config.ini`。每台 ChatServer 的 `[PeerServer]` 都要列出其他实例，
并为每个对端建立 5 个 stub；扩容时必须同步修改 StatusServer 和所有 ChatServer 的配置。实例
数为 N 时，配置关系与预建 stub 数量接近 `N × (N - 1)`，发布和连接管理成本会快速增加。

规模扩大后应引入服务注册与发现：ChatServer 用租约注册 TCP/gRPC 地址和健康状态，StatusServer
从注册表选择实例；跨服客户端按需创建并复用 channel，监听实例变更。另一种方案是通过消息
总线或专门路由层转发，降低全互连，但会增加中间跳和运维组件，需要根据消息量与故障模型取舍。

面试官会继续追问：为什么当前两台实例仍选择直连？两台时实现简单、链路短，也便于学习 gRPC；
承认它的扩容成本，说明达到什么规模或出现什么运维痛点后再演进，比直接堆注册中心更可信。



###  Qt 客户端有几万条会话或聊天记录时还能流畅吗？

当前会话和联系人使用 `QListWidget + setItemWidget`，聊天记录则为每条消息创建
`ChatItemBase`、`BubbleFrame`、`QTextEdit/QLabel` 等多个 QWidget。数据量小时实现直观，但大量
widget 会增加对象数量、布局计算、重绘和内存开销。当前“加载更多”和聊天历史头插也仍是
TODO，不能声称已经支持大规模历史消息。

改进方向是分页加载并限制内存窗口：列表改用 `QListView + QAbstractItemModel + delegate`，
聊天记录只保留当前可视窗口附近的数据，历史消息异步加载并在头插后补偿滚动位置；图片先用
缩略图和缓存，后台解码后回 GUI 线程更新。优化前应先用 Qt Creator Analyzer 或自建埋点测量
首次加载、滚动帧率、内存占用和图片解码耗时。


## 两个高压问题的回答分层

### “你用了 I/O 线程池，所以业务已经能并行处理了吗？”

危险回答：

> 是的，线程数等于 CPU 核数，所以所有请求都会并发处理。

问题在于它把 socket I/O 并发等同于业务并发，与当前单个 `LogicSystem` worker 的代码不符。

可过回答：

> I/O 回调由多个 io_context 线程处理，完整消息进入 LogicSystem 队列后由一个业务线程消费。
> 所以网络收发可并发，但业务处理目前串行，慢 SQL 或 RPC 会成为瓶颈。

强回答：

> 当前除了单 worker 外，DealMsg 还在执行 handler 时持有队列 mutex，会反向阻塞 I/O 线程
> 入队。我会先缩小锁范围，再按 uid 或 session 分片业务队列，保证同一会话有序、不同会话
> 并行；用队列等待时间、长度和 P99 业务耗时验证改造，而不是只增加线程数。

### “你的项目能支持多少并发？”

危险回答：

> 支持两万高并发，因为测试能建立两万个连接。

可过回答：

> 当前测试只测两台 ChatServer 在本机能保持的空闲 TCP 连接数，结果还可能先受客户端临时端口
> 限制，所以不能等价为两万并发消息。项目目前没有足够证据给出消息 QPS。

强回答：

> 我会把容量结论拆成连接容量、登录吞吐和消息吞吐，分别报告环境、并发模型、持续时间、
> 成功率、P95/P99、CPU/内存和队列长度。现有测试只覆盖第一项；下一步会用多机压测避免单
> 客户端端口上限，并加入登录和跨服消息场景找到真正瓶颈。
