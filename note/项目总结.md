# 即时通信系统的设计问题

## 为什么同时使用 HTTP、TCP 和 gRPC

HTTP 适合注册、验证码和登录等请求响应。聊天连接需要服务端主动通知，因此客户端建立持续的 TCP 会话。内部服务使用 protobuf 描述 gRPC 接口，供 C++ 服务和 Node.js 验证码服务共同使用。

资源传输独立处理文件和分片，ChatServer 只处理资源引用及消息状态。音视频页面经 WebRTC 连接 ZLMediaKit，聊天 TCP 承载通话邀请和控制信令。

服务拆分带来独立资源管理，也引入多个网络端点、依赖超时和跨系统一致性问题。实际职责与端口见 [全栈聊天室](全栈聊天室.md)。

## 登录为什么需要第二次身份校验

HTTP 验证过的账号与新建 TCP 连接没有天然关联。网关通过 StatusServer 获取聊天地址与 token，客户端再在 TCP 上提交 `uid/token`，ChatServer 校验后才把 UID 绑定到 session。

UID 标识用户，session ID 标识连接，token 是凭据。后续请求应使用认证 session 的身份检查客户端字段，不能只根据 JSON 中的 `fromuid` 授权。

当前 token 保存在 `utoken_<uid>`，没有 TTL 或一次性消费；签发使用时间戳与伪随机值组合。部署时还需独立考虑 TLS、凭据随机性、有效期与撤销策略。

## 保存与送达分别表达什么

| 状态 | 事实来源 | 可恢复方式 |
| --- | --- | --- |
| 已保存 | MySQL 提交成功 | 正式历史查询 |
| 已进入实时投递路径 | 本机发送或跨服调用结果 | 之后仍可查历史 |
| 对端已展示 | 接收端展示 ACK、`displayed_at` | 历史中的展示状态 |
| 对端已读 | 会话已读游标、消息 `status` | 历史与已读游标同步 |

先提交再投递，让在线路由失效时消息仍可通过历史恢复。投递过程中网络错误可能使通知遗漏或重复；缓存使用正式 ID 去重，不能因此宣称端到端只执行一次。

展示 ACK 和已读游标分开保存，可以让展示状态与用户阅读进度独立演进。客户端状态只单调提升，迟到通知不能把已读降成待确认。

## 四种消息标识为什么不能混用

| 标识 | 所属范围 | 使用目的 |
| --- | --- | --- |
| TCP 协议 ID | 请求或通知类型 | 分发登录、发送、历史、回执等处理器 |
| `msgid` | 客户端提交的逻辑消息 | 对应乐观气泡与发送结果 |
| `message_id` | 服务端正式消息 | 正式历史、同步游标、本地去重 |
| `thread_id` | 私聊或群会话 | 查找消息集合、成员与权限 |

当前文本保存为普通插入，相同 `msgid` 重发可能生成新的 `message_id`。按正式 ID 去重只能处理同一正式记录的重复投递，无法把两条新记录自动认作一次业务提交。

## 会话、消息与资源为什么分开存储

会话保存参与者和摘要，消息保存按正式 ID 排列的内容，资源表述文件身份及可信元数据。私聊用户对采用归一化顺序及唯一约束，避免并发创建两个会话；群消息只保存一行，以 `recv_id=0` 表示群内扇出。

二进制放在资源服务，数据库保存 `resource_id`、类型、名称、大小和图片尺寸等信息。ChatServer 通过资源服务核验已完成资源，下载端再核验当前身份、成员关系与资源归属。

这要求区分“文件已上传”和“聊天消息已提交”。上传成功后业务提交仍可能失败，已知资源 ID 也不代表拥有下载权限。

## 历史分页为什么限制实际字节数

固定 `page_size` 无法限制 JSON 的最终长度：中文 UTF-8、转义、文件名和资源字段都会改变序列化大小。`LogicSystem.cpp` 的历史响应逐条试装，并按实际紧凑 JSON 大小控制在 4 KiB。

分页游标停在已成功返回的正式消息 ID。单条消息连同响应字段都放不下时返回 `MessageTooLarge`，保持游标不变，避免静默遗漏。

客户端每账号独立 SQLite，消息、会话摘要和游标需要一起提交。游标先推进、消息未写入会造成下次同步跳过数据；重复响应则应通过正式 ID 合并。

## 群管理如何处理并发和迟到事件

群管理把群状态、角色权限、成员身份版本和业务操作结果放入数据库事务。群行锁串行化相关管理动作，唯一约束限制重复待处理准入，`operation_id` 关联重复业务提交。

| 版本 | 解决的问题 |
| --- | --- |
| 群 `version` | 判断共享资料与成员集合是否变化 |
| `membership_version` | 区分退出、踢出、重入和角色变化 |
| `announcement_version` | 防止旧公告编辑覆盖新正文 |
| `avatar_version` | 防止迟到下载覆盖新头像 |

成员失效保留墓碑，重新加入继续增加版本。迟到踢人通知应匹配旧身份，群失效也只使该群只读，不注销整个账号。更多事务知识见 [群聊事务](总结群聊.md)。

## 重复登录为什么还要比较 session ID

Redis 登录锁控制遵守相同 key 的身份更新，但旧连接回调可能在新连接建立后到达。按 UID 无条件删除会话或在线键，会删掉新身份。

本机会话移除比较 session ID，远端清理也在登录锁内检查 `usession_<uid>`。跨服踢人携带旧 session ID，源端等待成功再写新路由。租约超时与进程崩溃仍会留下边界，需要结合实际路由与会话状态排查。

## I/O 并发与业务并发有什么区别

Asio 线程池可以同时维护多条连接。ChatServer 的 `LogicSystem` 使用一个消费线程处理业务队列，慢 SQL 和同步 RPC 会阻塞后续业务；心跳直接在会话路径响应。

每个 session 的发送队列串行写出，防止两个 `async_write` 交叉。容器锁、对象生存期、socket 执行器与数据库行锁分别保护不同范围，不能用增加 I/O 线程数替代这些约束。

按会话固定分配多个业务 Worker 是可研究的设计，当前聊天服务未采用。分析方法见 [业务调度与性能分析](项目优化.md)。

## 怎样解释测试与容量结果

| 层级 | 可以直接观察 | 仍需其他层证明 |
| --- | --- | --- |
| 帧解析测试 | 字节分段、帧边界、非法输入行为 | 真 socket 生命周期 |
| 数据库事务测试 | 提交、回滚、权限和唯一约束 | 在线路由与客户端展示 |
| SQLite 与 Widgets 测试 | 缓存状态、窗口相关行为 | 完整网络部署 |
| 真实服务 smoke | 进程、协议和跨服协作 | 更广的故障组合与持续负载 |
| 容量测试 | 指定环境与负载下的连接表现 | 其他机器或业务吞吐上限 |

连接容量同时受客户端临时端口、缓冲、服务端句柄、内存和依赖限制。业务压测需明确登录与心跳、消息大小、跨服比例、数据库规模，采集吞吐、延迟分位数和错误率。运行要求见 [测试](测试.md)。
