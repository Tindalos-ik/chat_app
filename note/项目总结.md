# 项目总结：分布式即时聊天系统

> 本文以仓库当前代码、`proto/message.proto`、SQL 脚本和配置为准，描述的是**项目事实**，不等同于任一开发者的个人贡献范围。面试时应只陈述自己实际负责、能展示代码和能解释取舍的部分。

## 1. 项目定位

这是一个面向 Windows 本地开发与联调的 C++ 分布式即时聊天系统。它包含 Qt 6 桌面客户端、HTTP 网关、验证码服务、登录与路由服务、两台 TCP 聊天服务和资源服务。

项目的重点不只是“能聊天”，而是把一条私聊消息拆成可以审计的状态和链路：身份校验、落库、同服或跨服推送、客户端本地缓存、展示确认、已读确认、历史补偿和图片资源鉴权下载。

当前工程不是已经完成多机容灾和公网安全加固的生产系统：gRPC/TCP/HTTP 仍以明文通道为主，Redis/MySQL 也是单点配置。它适合定位为“实现了分布式聊天核心链路，并明确记录了边界”的工程项目。

## 2. 架构与职责边界

```text
Qt 桌面客户端
  ├─ HTTP 8080 ───────────────► GateServer
  │                               ├─ gRPC 50051 ─► VarifyServer ─► SMTP / Redis
  │                               └─ gRPC 50052 ─► StatusServer ─► MySQL / Redis
  │                                                        │ 选择 ChatServer、签发/校验 token
  ├─ TCP 8090 / 8091 ────────► ChatServer1 / ChatServer2
  │                               ├─ MySQL：会话、消息、已读/展示状态
  │                               ├─ Redis：在线路由、在线数、token、缓存、分布式锁
  │                               ├─ gRPC：跨服消息、回执、互踢
  │                               └─ gRPC 50057 ─► ResourceServer：图片完成态核验
  └─ TCP 9090 ───────────────► ResourceServer ─► uploads
                                      ├─ StatusServer：下载 token 校验
                                      └─ MySQL：私聊成员关系与资源归属校验
```

| 组件 | 技术与端口 | 当前职责 |
| --- | --- | --- |
| `chat_app desktop` | Qt 6、HTTP/TCP、SQLite | 登录、好友与私聊 UI、长连接、图片传输、本地缓存、同步和消息状态展示 |
| `GateServer` | Boost.Beast、gRPC、8080 | HTTP 注册、验证码、登录、重置密码和账号资料入口 |
| `VarifyServer` | Node.js、gRPC、50051 | 生成短验证码，写 Redis 过期键并经 SMTP 发送邮件 |
| `StatusServer` | gRPC、50052、Redis | 依据在线数选择 ChatServer，签发并校验 TCP 登录 token |
| `ChatServer1/2` | Boost.Asio、gRPC、8090/8091、50055/50056 | TCP 长连接、私聊建会话、消息持久化、在线/跨服路由、回执转发 |
| `ResourceServer` | Boost.Asio、gRPC、9090/50057 | 图片分片上传、断点续传、完成态核验、鉴权分片下载 |
| MySQL | X DevAPI、33060 | 用户/好友关系、私聊会话、消息、图片可信元数据、已读和展示状态 |
| Redis | 6379 | 验证码、登录 token、用户路由、在线计数、用户资料缓存、登录锁 |

## 3. 已实现的关键链路

### 3.1 登录、选服与 TCP 身份绑定

1. Qt 通过 HTTP 调 GateServer 验证账号密码。
2. GateServer 经 StatusServer 选择在线数较低的 ChatServer，并获得 `uid + host + port + token`。
3. 客户端对该 ChatServer 建立 TCP 长连接，发送 uid 与 token；ChatServer 校验后才绑定 `session -> uid`、写入在线路由并加载基础数据。
4. 同账号重复登录使用 `login_lock_<uid>` 串行化；旧会话由本机关闭或 gRPC `NotifyKickUser` 跨服关闭，并以 session id 防止陈旧踢人请求误伤新会话。

选服依据是 Redis 的 `login_count` 最小值，负载相同时轮询。这是横向扩展入口，不是健康检查：异常退出、网络分区或 Redis 路由残留仍需要租约、探活和故障摘除来治理。

### 3.2 文本/图片消息与三阶段状态

私聊先创建或复用唯一的 `chat_thread/private_chat`，随后消息写入 `chat_message`。`message_id` 是服务端单调主键，用于幂等、同步和游标；`thread_id` 归属会话；客户端 `msgid` 用于把发送前气泡与服务端确认关联。

发送方收到的确认明确区分：

| 状态字段/状态 | 含义 | 不能推导出的事实 |
| --- | --- | --- |
| `persisted=true` | 消息已经写入 MySQL，可经历史同步恢复 | 对端在线、对端已看到 |
| `realtime_delivered=true` | 已进入同服 TCP 或跨服 gRPC 的实时投递路径 | 对端 UI 已渲染 |
| `peer_displayed=true` | 对端客户端已经把消息实际绘制到当前会话 | 对端已完整阅读 |
| `status=1` / 已读 | 接收方已对会话提交已读游标 | 发送端必然在线收到通知 |

文本和图片均可同服直推；跨服时由源 ChatServer 根据 Redis 中的用户路由调用对端 gRPC。图片二进制不经过 ChatServer：客户端先把图片传至 ResourceServer，ChatServer 使用 gRPC 核验资源已完成、文件类型和元数据后才写入图片消息。

### 3.3 展示 ACK、已读回执与未读数

- `1036`：接收端仅在消息实际进入当前聊天视图后发送展示 ACK；服务端幂等写入 `displayed_at`。
- `1037`：ChatServer 将“对端已展示”通知发送方；发送端气泡可以提升为已显示。
- `1038`：用户进入会话后按会话内 `message_id` 游标提交已读。
- `1039`：服务端更新仅属于该接收者的消息 `status=1`，并将已读游标通知发送方。
- 客户端 SQLite 的 `delivery_state` 单调提升为已保存、已实时投递、已展示、已读；对实时通知和历史同步使用 `message_id` 去重，迟到包不能把更高状态回退。

### 3.4 历史同步和本地缓存

每个登录 uid 使用独立 SQLite 文件。客户端维护会话摘要、消息表、附件表和每个会话的同步游标；实时通知与登录后增量同步写入同一 SQLite 事务，以保证消息、未读数、最后消息和游标尽量一致。

`1030` 历史响应除遵守 `page_size` 外，还以最终紧凑 JSON 的实际序列化字节数限制为 **4 KiB**。服务端逐条试装，放不下则以前一条消息作为 `next_message_id` 返回 `load_more=true`；单条消息自身不能放入帧时返回 `MessageTooLarge (1016)`，不截断、不静默跳过、不推进游标。

### 3.5 图片资源上传、下载和鉴权

资源服务负责分片上传、断点续传和分片下载。ChatServer 只保存 ResourceServer 重新核验得到的 `resource_id`、MIME、尺寸、大小和文件名等可信元数据，而不保存服务器绝对路径或转发二进制。

下载 `1007` 必须携带 `uid`、登录 `token`、`thread_id` 与 `resource_id`。ResourceServer 先向 StatusServer 校验 token，再查询聊天库确认：请求者是该私聊成员，且该资源属于该会话中的图片消息。无权限/归属不符返回拒绝，认证依赖不可用也默认不放行。客户端将这类错误与普通网络错误区分显示，并为可重试的下载失败提供“重试/取消”。

### 3.6 TCP、并发与清理

ChatServer 的连接处理采用 Asio Reactor 模型：主接收器持续 `async_accept`，每条 session 分配到 `AsioIOServicePool` 中一个 `io_context`；读路径先读固定包头、再读包体，业务消息转交 `LogicSystem` 队列处理。每条 session 保持独立发送队列，队列从空转非空时发起一次异步写，写完成后串行发送下一条，避免多次 `async_write` 交错。

客户端每 20 秒发送 `1023` 心跳，60 秒未收到有效响应则断开；服务端每 10 秒扫描，60 秒未收到完整合法包也进入统一清理。当前没有完整的指数退避重连、重新选服和恢复登录状态机。

## 4. 数据设计与一致性取舍

| 对象 | 关键约束/索引 | 解决的问题 |
| --- | --- | --- |
| `private_chat` | `(user1_id, user2_id)` 唯一，按 uid 归一化排序 | 同一对用户最多一个私聊 thread |
| `chat_message` | 全局递增 `message_id`，`(thread_id, message_id)` 索引 | 实时/历史去重、增量同步、按会话分页 |
| `chat_message.displayed_at` | 与 `status` 分离 | 已展示不等于已读 |
| `chat_message.status` | `0=未读, 1=已读, 2=撤回` | 服务端已读状态与未读统计 |
| SQLite `local_chat_message` | `message_id` 主键、`INSERT OR IGNORE` | 重复推送和重复同步幂等落库 |
| SQLite 同步游标 | 每个 `thread_id` 单独维护 | 恢复历史和断线后的增量拉取 |
| Redis `uip_<uid>` / `usession_<uid>` | 在线实例和会话标识 | 同服/跨服路由与防陈旧互踢 |

这里的核心取舍是“先持久化，再尽力实时推送”。因此跨服投递失败后，发送端仍应看到已保存，而不是被诱导重复发送；接收端下次登录或同步时可以补到消息。它不是严格的端到端 exactly-once 投递：当前依赖服务端 `message_id` 和客户端 SQLite 幂等来收敛重复。

## 5. 测试事实与当前边界

仓库已有 GoogleTest/CTest 的 `connection_capacity_test`，它会分别对 `ChatServer1:8090` 与 `ChatServer2:8091` 逐步建立并保持真实 TCP 连接。2026-09-09 的本机记录显示：单客户端总计约 1.6 万空闲连接时先遇到 Windows 客户端 `WSAENOBUFS`/动态端口限制，并不能据此宣称服务器上限为 1.6 万。

当前尚未覆盖为独立自动化测试的高风险路径包括：TCP 半包/粘包/非法包头、登录与跨服路由、MySQL 事务与并发幂等、Redis 清理竞态、资源下载鉴权、回执状态机、Qt 收包解析和带业务负载的端到端回归。面试中应如实说“已有容量集成测试和静态/联调验证”，而不是说“测试全覆盖”。

同样需要主动承认的安全与可用性边界：token 需要进一步增加 TTL/轮换与一次性消费策略；外部通道应使用 TLS；配置中的明文密钥应迁至环境变量或密钥管理；Redis/MySQL 尚未做高可用；ChatServer 健康检查、路由租约、自动摘除、可靠队列、重连和可观测性仍是后续工作。

## 7. 高价值面试问题与答题边界

### 1. 为什么不能把“已入库”直接当成“已送达”？

入库只证明 MySQL 已成功提交；实时投递还依赖目标在线路由和本机/跨服网络；展示则需要对端 UI 实际处理。项目因此分别回传 `persisted`、`realtime_delivered` 和 `peer_displayed`。跨服投递失败仍保留“已入库”，接收端可由后续历史同步补偿。

继续追问：如果发送端在 1037 到达前重连，如何恢复？当前由历史记录中的 `displayed_at` 恢复；实时通知只是加速路径，不能宣称端到端实时通知绝不丢失。

### 2. 展示 ACK 和已读为什么要分开？

展示 ACK 是界面事实：消息确实被放进当前聊天视图；已读是用户语义：会话已读到某条 `message_id`。二者分别由 `displayed_at` 与 `status` 表示，避免“通知栏渲染”或“历史加载”被误认为用户已读。

继续追问：重复 ACK 或乱序 ACK 怎么办？服务端写入应幂等，客户端 delivery state 只能单调提升，不能被迟到包降级。

### 3. 为什么历史接口要按实际 JSON 字节数，而非只限制 `page_size`？

图片元数据、文件名转义和 Unicode 会使固定 100 条消息超过 TCP 协议包体边界。1030 用实际紧凑序列化后的 JSON 测量，在 4 KiB 内逐条装载；一条都放不下时返回明确的 `MessageTooLarge`，避免截断数据或游标卡死。

### 4. 如何避免私聊图片越权下载？

不能只靠难猜的 `resource_id` 或 URL。下载端携带 uid、token、thread id；ResourceServer 校验 token、私聊成员关系，并确认资源确实归属这个会话的图片消息。鉴权依赖不可用时默认拒绝，这就是失败关闭。

### 5. 为什么图片二进制不通过 ChatServer 转发？

ChatServer 负责消息状态、路由和持久化元数据；ResourceServer 更适合处理文件分片、磁盘、断点续传和文件类型核验。分离后避免聊天服务的内存和 gRPC 被大文件占用，但代价是需要资源核验、元数据一致性和独立下载鉴权。

### 6. 你怎样处理同账号两次登录的竞态？

应描述锁内读取旧路由、使用 session id 条件踢人、踢人成功后写新路由的顺序；旧服收到跨服请求时也核验 session id。Redis 锁租约、进程崩溃、路由过期和多命令删除仍有边界，生产实现可以使用 Lua 比较删除、路由 TTL 和心跳续租进一步收敛。

### 7. 这个连接容量数据说明了什么？

正确回答是：它证明当前环境下测试流程能维持约 1.6 万空闲连接，且先观察到客户端侧缓冲/端口限制；它不等于服务端最大连接数，更不能推出业务消息吞吐。要测服务端真实能力，应从多源 IP、带登录心跳和业务消息的负载下采集延迟、错误率、CPU、内存、队列长度和数据库连接池等待。

### 8. 如果要把这个项目继续做成可部署系统，优先级是什么？

建议按风险排序：先加 TLS、token TTL/轮换和密钥管理；再加 ChatServer 注册租约、健康检查和客户端重连；补充协议/回执/资源鉴权的自动化测试；最后建设日志、指标、告警、追踪、数据库备份与 Redis/MySQL 高可用。没有完成这些工作前，不应使用“生产级高可用”或“高并发稳定上线”等表述。
