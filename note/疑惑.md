###  uid 和 token 

**uid = 你是谁，token = 一张一次性通行证**，配套的 host/port = 去哪里。

* **uid**：用户唯一标识。注册时从 `user_id` 表分配，永不改变。数据库主身份、好友关系、消息路由、Redis key 全用它。
* **token**：一次性登录凭证。StatusServer 在 `GetChatServer` 时生成（纳秒时间戳 XOR 随机数转 hex），记在内存 `_tokens[uid]`；ChatServer 收到 TCP 登录时调 `Login(uid, token)` 校验。
* **host/port**：本次登录被分配到的聊天服务器地址（负载均衡的结果），客户端用它建 TCP 长连接。

**为什么必须有 token**：密码已在 HTTP 通道验证过，但 TCP 是一条全新通道，客户端只说"我是 uid 1002"谁都能冒充。token 把 HTTP 通道验证过的信任转移到 TCP 通道，且 TCP 上永远不出现密码。这就是"HTTP 验身份、TCP 验凭证"的双通道设计。

局限：token 存在 StatusServer 内存 map 里（不是 Redis），重启全失效、无 TTL、多实例不一致；生成方式属于"够用但不是密码学安全随机"。


### ChatServer 的 UserMgr 是干什么的

`UserMgr` 维护一张“用户 uid → TCP 会话 CSession”的内存映射。用户登录 ChatServer 成功后，把当前会话保存进去；其他用户发来好友申请或聊天消息时，就可以根据目标用户的 uid 找到对应会话，并通过 `CSession::Send()` 推送给客户端。

| 操作 | 作用 |
| --- | --- |
| `SetUserSession(uid, session)` | 登录成功，把用户和当前 TCP 连接绑定 |
| `GetSession(uid)` | 根据 uid 查找本机在线用户的会话 |
| `RmvUserSession(uid, session_id)` | 连接断开时移除绑定 |

参考项目 `llfcchat/server/ChatServer` 中，`UserMgr` 还负责防止旧连接断开时误删新连接：删除前会比较 `session_id`。当前 `ChatServer1/include/UserMgr.h` 只有接口，`src/UserMgr.cpp` 仍为空，登录、断开清理和聊天转发暂时还没有接入它，所以目前它只是预留的在线用户管理模块。

`CServer` 的 `_sessions` 是“session_id → CSession”，用于管理所有 TCP 连接；`UserMgr` 是“uid → CSession”，用于按用户身份快速找人。两张表用途不同，通常需要在连接断开时同时清理。


### ChatGrpcClient 的 GetBaseInfo 声明不兼容

如果 `ChatGrpcClient.h` 引入的 `data.h` 中有一个空的 `class UserInfo`，而 `MysqlMgr.h` 又定义了一个完整的 `struct UserInfo`，即使名字相同，编译器也会把它们视为冲突的类型。这样会导致 `ChatGrpcClient.cpp` 中的函数定义与头文件声明不兼容，出现 IntelliSense 147。

正确做法是只保留一份 `UserInfo` 定义，放在 `data.h` 中，`MysqlMgr.h` 通过 `#include "data.h"` 复用；如果函数需要在内部替换或填充智能指针，还要让声明和定义统一使用 `std::shared_ptr<UserInfo>&`。Windows 下头文件大小写不敏感，但 Linux 下敏感，`#include "UserMgr.h"` 也要和实际文件名一致。


### VS Code 中 Git push 失败

如果远程地址是 `git@github.com:用户名/仓库.git`，VS Code 的源代码管理插件最终仍然调用本机 Git 的 SSH。出现 `Connection closed ... port 22` 时，通常还没有进行 SSH 密钥或仓库权限验证，而是网络无法连接 GitHub 的 SSH 服务。

排查顺序是先检查 `github.com:22` 是否可达，再检查 HTTPS `443`。如果两个端口都不通，切换 SSH/HTTPS 都没有用，需要先连接 VPN、配置正确代理或调整防火墙；网络恢复后，再处理 SSH key、登录凭据和仓库权限问题。



##  Qt 信号槽为什么高并发更安全

核心是**连接类型 + 线程亲和性**：

* 跨线程连接自动用 `QueuedConnection`：调用连同参数打包成 `QMetaCallEvent` 投递到接收者线程的事件循环，**槽在接收者自己的线程串行执行，不用为接收者加锁**；
* 多线程同时 emit 同一信号时事件排队处理（TcpMgr 注释"类似排队的效果"）；
* connect 的接收者 context 销毁时连接自动断开，不会出现"回调时对象已死"的悬垂调用；
* QueuedConnection 把调用串行化，避免槽被同一信号重入打断。

注意事项：同线程默认直连，"并发安全"主要指跨线程；QueuedConnection 有参数拷贝开销；两个对象共享同一份可变数据时该加锁还得加锁。



### MySQL 该存什么、Redis 该存什么

| 数据 | 存储 | 理由 |
| --- | --- | --- |
| 账号/密码、用户资料、好友关系、好友申请、聊天记录 | MySQL | 强一致、持久、要查询 |
| 验证码、token、在线状态、未读数、离线消息暂存 | Redis | 高频、短生命周期、要过期 |

用户数据四张表（llfc1）：`user`（账号+资料）、`user_id`（uid 分配器）、`friend`（双行存储+备注）、`friend_apply`（申请状态机）。判断标准一句话：**要永久、要查询、要事务的进 MySQL；要快、要过期、高频写的进 Redis。**



###  mysqlcppconnx（X DevAPI）要点

* vcpkg 端口名是 `mysql-connector-cpp`（README 写 `mysqlcppconnx` 是笔误），CMake 链接目标 `mysqlcppconnx`，头文件 `<mysqlx/xdevapi.h>`；
* 走 X Protocol，端口 33060（经典 API 才是 3306）；
* 链式调用：`session->sql(sql).bind(...).execute().fetchOne()`，返回 `SqlResult` → `Row` → `row[i].get<T>()`；
* `Row` 有 `operator bool()`，`if (!rows)` 就是没查到；
* **列下标从 0 开始**（经典 API 从 1 开始）；
* 参数化绑定 `?` + `bind()` 防 SQL 注入；
* 出错抛异常（`std::exception`），每个数据库方法必须 try/catch。



### 聊天记录为什么用 QScrollArea + QVBoxLayout，而列表用 QListWidget

会话列表/联系人列表是"记录行"，聊天记录是"内容流"，两者本质不同，所以容器不同。

**列表为什么用 QListWidget**：每行结构统一（头像 + 名字 + 摘要/时间 + 红点），行高固定（ChatUserWid 的 sizeHint 固定 260×75）。这种"一堆结构相同的记录"正是 QListWidget 的主场——item 存数据、`setItemWidget` 塞控件，还附带选择、点击、键盘导航等列表语义。

**聊天记录为什么用 QScrollArea + QVBoxLayout**：

1. **高度动态且随宽度变化**：文字气泡换行高度不定，layout 按各 widget 的 sizeHint 自动重排，窗口拉宽后文字重新换行、高度自动重算；QListWidget 的 item 高度是插入时定死的 sizeHint，缩放后不会自动重算，要么变形要么手动遍历重算。
2. **消息流有左右对齐、分隔、分组语义**：自己发的靠右、对方靠左，穿插时间分隔条和系统提示，连续消息间距要小。QVBoxLayout 天然支持每项独立对齐和 spacing；QListWidget 里对齐要自己在行内做，分隔条变成一种特殊行，语义绕。
3. **滚动行为特殊**：新消息自动滚到底（`setSliderPosition(maximum())`）、往上翻加载旧消息时头插并保持滚动位置（offset 补偿）。QScrollArea 的 scrollbar 直接归自己管；QListWidget 是行模型，靠 `scrollToItem`，头插 + 位置补偿很别扭。
4. **没有多余语义**：QListWidget 自带选择高亮、item 角色、拖拽等列表功能，聊天气泡完全用不上。

| 维度 | 列表（会话/联系人） | 聊天消息区 |
| --- | --- | --- |
| 本质 | 结构统一、固定行高的记录 | 高度动态、混合内容的流 |
| 换行/缩放 | 不需要 | 必须自动重排 |
| 对齐语义 | 每行一个样式 | 左右气泡、时间分隔、分组 |
| 滚动 | 滚到底即可 | 自动贴底、头插补偿 |
| 合适容器 | QListWidget | QScrollArea + QVBoxLayout |

> 注意：QListWidget 底层也是一个 QAbstractScrollArea，所以问题不是"要不要滚动"，而是"item 行模型 vs widget 流"。消息量巨大（几千条以上）时的正确方案是 QListView + 自定义 delegate（真虚拟化，只绘制可见行），教学场景和中小规模用 layout 方案更直观。



### 为什么只放一个组件也要用布局

布局（layout）干的事不是"把多个组件摆开"，而是**管理组件的几何**：位置、尺寸、以及父窗口缩放时怎么跟着变。哪怕只有一个组件，这些问题照样存在。

**没有布局会怎样**：`new QScrollArea(this)` 后不管它，得到的滚动区域尺寸是 0×0（或默认值）、位置不对，父窗口拉大它也不会跟着变。要让它铺满父窗口，只能自己重写 `resizeEvent` 手动 `setGeometry(rect())`——这等于在**手写一个布局**，还得考虑边距、滚动条占位、内容变化，写几行就漏。

**有了布局会怎样**：

```cpp
QVBoxLayout* pMainLayout = new QVBoxLayout();
this->setLayout(pMainLayout);
pMainLayout->setContentsMargins(0, 0, 0, 0);
pMainLayout->addWidget(m_pScrollArea);   // 表达的是：占满父窗口、四周边距 0
```

之后父窗口变大变小、边距要不要留、将来要不要再加子控件（提示条、日期条），Qt 全部自动处理，不用写一行 resizeEvent。

| | 不用布局 | 用布局 |
| --- | --- | --- |
| 初始位置/尺寸 | 靠运气或手写 setGeometry | 自动按策略填满 |
| 父窗口缩放 | 不动，要自己写 resizeEvent | 自动重排 |
| 边距控制 | 自己加 | `setContentsMargins` 一行 |
| 以后加第二个组件 | 重写一堆几何代码 | `addWidget` 一行 |

> 替代思路：如果"反正只有一个滚动区域"，也可以让类直接继承 QScrollArea，少包一层；但"QWidget + 内部布局"是 llfc 和本项目采用的标准写法，提升到 .ui 里最灵活，不用改。



### 布局里的"弹簧"：`addWidget(new QWidget(), 100000)` 是干什么的

（ChatView 内容布局里的这行）注意：**100000 不是高度**，那个 QWidget 也不是"高组件"——它是一个 sizeHint 为 0×0 的空 widget，第二个参数是**拉伸因子（stretch factor）**，是比例/权重，不是像素。

它的作用：**把布局里的"剩余空间"全部吸走**。

**为什么需要它**：如果内容布局里只有气泡、没有弹簧，消息很少（比如 2 条）而窗口很高时，QVBoxLayout 会把多余空间按各 widget 的 sizePolicy 分掉，气泡可能被**拉高**或空间分配混乱，不再保持自然高度。有了 stretch=100000 的弹簧：

```text
窗口很高、消息很少时：
┌─────────────────────┐
│ 气泡1               │  ← 保持自然高度
│ 气泡2               │
│                     │
│   （弹簧 stretch）   │  ← 剩余空间全被它吃掉
│                     │
└─────────────────────┘
```

* **视觉上**：气泡永远挤在顶部、不被拉长，多余空间全变成弹簧占据的空白；
* **结构上**：弹簧是布局里固定的一项，所以"尾插" = 插到 `count()-1`（弹簧前面），消息永远在弹簧上方——这就是 `appendChatItem` 里 `insertWidget(count()-1, item)` 的由来；
* **消息多时**：内容超过窗口高度，弹簧自动缩到 0，滚动条出现，正常滚动；它只在"内容不满"时才撑开。

> 等价写法是 `addStretch(100000)`（加的是 spacer 而不是空 widget），效果一样；llfc 用 `addWidget(new QWidget(), 100000)`，照抄没问题。



### ChatDialog 发送文本消息时，两个信号分别有什么用？

发送入口是 `ChatDialog::on_send_btn_clicked()`。点击发送按钮会触发它；输入框
`MessageTextEdit` 还重写了 `keyPressEvent()`，所以按 **Enter（不按 Shift）** 时会先
`emit send()`，构造函数中这条连接再调用同一个发送函数：

```cpp
connect(ui->input_edit, &MessageTextEdit::send,
        this, &ChatDialog::on_send_btn_clicked);
```

`send()` 只是“用户要求发送”的 UI 信号，本身没有文本参数，也不碰网络。实际内容仍在
`on_send_btn_clicked()` 内通过 `ui->input_edit->getMsgList()` 读取。`getMsgList()` 会把编辑器
里的内容拆成 `MsgInfo`：普通文字是 `"text"`，图片和文件分别是 `"image"`、`"file"`。

一次文字消息的当前链路可以这样看：

```text
点击发送 / Enter
        |
        v
ChatDialog::on_send_btn_clicked()
        |-- 创建右侧 TextBubble，立即显示在聊天区
        |-- 为文字创建 UUID，组装 {content, msgid}
        |-- emit sig_append_send_chat_msg(TextChatData)
        `-- emit TcpMgr::sig_send_data(1017, JSON)
                                      |
                                      v
                         TcpMgr::slot_send_data()
                         写入 [2 字节消息 ID][2 字节长度][JSON] 到 QTcpSocket
```

这里最容易混淆的是两个“发送”信号：

| 信号 | 参数 | 当前作用 | 是否直接发网络包 |
| --- | --- | --- | --- |
| `MessageTextEdit::send()` | 无 | 回车快捷键通知 ChatDialog 执行发送流程 | 否 |
| `ChatDialog::sig_append_send_chat_msg()` | `std::shared_ptr<TextChatData>&` | 把一条本地发出的文字消息交给“消息列表/送达状态”一类模块；其中有 `msgid`、文字、发送者和接收者 UID | 否 |
| `TcpMgr::sig_send_data()` | `ReqId`、`QByteArray` | 把已经序列化好的业务数据交给统一的 TCP 管理器 | 是，间接地；其槽最终调用 `_socket.write()` |

#### `sig_append_send_chat_msg` 到底是给谁的？

它的参数 `TextChatData` 定义在 `userdata.h`：

```cpp
struct TextChatData {
    QString _msg_id;
    QString _msg_content;
    int _from_uid;
    int _to_uid;
};
```

因此它表达的不是“把文字发到服务器”，而是：**本地刚提交了一条可由 `msgid` 唯一追踪的消息**。
常见接收槽会把它暂存为“发送中”，以便收到 `ID_TEXT_CHAT_MSG_RSP` 后按 `msgid` 改为已送达或失败，
也可用于更新会话列表摘要、写本地历史记录、重发失败消息。

但在当前仓库里，搜索 `sig_append_send_chat_msg` 只能找到声明和 `emit`，没有任何 `connect` 接收它。
所以它现在是**预留的业务通知**：`emit` 后不会产生后续效果，也不会影响 TCP 发包。聊天气泡仍会立即显示，
因为它是前面直接调用 `ui->chat_data->appendChatItem(pChatItem)` 加进去的，并不是该信号加进去的。

#### 为什么 TCP 也设计成信号，而不是 ChatDialog 直接 `socket.write()`？

`TcpMgr` 是长连接的唯一拥有者。构造时它把自己的信号接回自己的槽：

```cpp
connect(this, &TcpMgr::sig_send_data, this, &TcpMgr::slot_send_data);
```

这样 ChatDialog、好友申请页、搜索页等模块只需要说明“发什么协议 ID 和 JSON”，不用持有或操作
`QTcpSocket`，包头编码也只维护一份。`slot_send_data()` 统一把请求 ID 和 JSON 长度写成大端
`quint16`，再调用 `_socket.write(block)`。同线程时这条连接默认是直接调用；若对象位于不同线程，
Qt 才会通过事件队列投递槽调用。它不是自动的网络发送队列，也不等于服务器确认已收到。

#### 为什么不直接把聊天文字写到 socket？

如果只是单机演示，当然可以写成下面这样：

```cpp
socket.write(ui->input_edit->toPlainText().toUtf8());
```

但这只能表达“有一串字节要写出去”，表达不了一条可被聊天系统正确处理的消息。TCP 是**连续字节流**，
不是一条条天然分开的消息：两次 `write()` 可能被对方一次读到，也可能一次 `write()` 被拆成多次读到。
因此至少需要长度边界；本项目统一使用：

```text
[2 字节请求 ID][2 字节 JSON 长度][JSON 消息体]
```

而 JSON 消息体也不能只有 `"你好"`，服务器还需要知道是谁发给谁、该按什么业务处理：

```json
{
  "fromuid": 1001,
  "touid": 1002,
  "textArray": [
    { "content": "你好", "msgid": "{uuid}" }
  ]
}
```

`fromuid`/`touid` 用于鉴权和路由，`msgid` 用于把服务端回包、失败重发、去重与本地“发送中”状态对应到
同一条消息；请求 ID `1017` 则让服务器把这个包识别为“文本聊天”，而不是登录、搜索或好友申请。

更重要的是职责边界。若 `ChatDialog` 直接持有 `QTcpSocket`，它既要管理输入和气泡，又要了解包头、连接状态、
粘包处理、协议 ID 和写入失败；搜索、好友申请等页面还会复制同一套代码。现在由 `TcpMgr` 统一封包和持有连接，
ChatDialog 只负责“把用户输入变成一条聊天请求”，以后更换传输方式、补断线重连或增加日志时，改动集中在网络层。

不过也不必把“分层”误解成每一步都必须有信号。对当前项目而言，**协议包头 + 结构化消息 + `TcpMgr` 统一发送**
是必要复杂度；`sig_append_send_chat_msg`、批量 `textArray`、送达状态则是为消息状态和扩展能力预留的复杂度。
后者尚未接上接收槽或服务端回包时，确实暂时没有实际收益。教学或最小可用版本可以先只发送一条
`{fromuid, touid, content, msgid}`，待服务端回包、离线消息、重发和多媒体消息真正实现后，再扩展为批量与状态机。

#### 为什么一个请求里要放多个 JSON 对象？

严格来说，当前格式不是把多个顶层 JSON 直接拼接：

```text
错误理解：  { ... }{ ... }{ ... }
实际格式：  { fromuid, touid, textArray: [ { ... }, { ... }, { ... } ] }
```

外层对象是一次 TCP 请求的“信封”，负责描述这批消息的发送者和接收者；`textArray` 是消息数组，
数组中的每个对象才是一条独立文本：

```json
{
  "fromuid": 1001,
  "touid": 1002,
  "textArray": [
    { "content": "第一条", "msgid": "id-1" },
    { "content": "第二条", "msgid": "id-2" }
  ]
}
```

这样设计主要有几个原因：

1. **一次请求可以承载多条消息**：网络包头、JSON 外层字段只需要写一次，减少频繁的小包；离线消息补发、
   输入框一次解析出多段文字时尤其方便。
2. **每条消息仍能独立追踪**：`msgid` 和 `content` 属于数组元素，服务端可以逐条存储、转发、去重，
   客户端也能按消息 ID 更新发送状态，而不是只能把整段文字当成一个不可分割的字符串。
3. **便于扩展**：以后单条元素可以增加时间、消息类型、回复引用等字段，而不必修改外层路由字段；
   外层也可以继续增加会话 ID、压缩标志等请求级字段。
4. **接收方处理更明确**：先读取 `fromuid`/`touid` 确定会话，再遍历 `textArray` 处理每一条内容，
   不需要猜测一长串文本中哪里是上一条消息的结尾。

当前 `ChatDialog::on_send_btn_clicked()` 会先积累文本元素，并在循环结束或文本累计到 1024 UTF-8 字节时发送一批。
图片和文件只走本地预览，尚未被伪装成空文本请求发送给服务端。

#### 当前实现应注意的边界

* 发送前会检查登录用户和当前聊天对象，未选中联系人时不会解引用空指针。
* 文本气泡仍采用乐观显示；客户端已注册 `ID_TEXT_CHAT_MSG_RSP`，目前把每个 `msgid` 的成功/失败写入日志，
  还没有把失败状态绘制到气泡或实现重发。
* `ID_TEXT_CHAT_MSG_REQ`（1017）已由 ChatServer1/2 注册。服务端只接受与当前 TCP 会话 UID 相同的
  `fromuid`，并统一使用 `textArray`；同服直接推送，跨服通过 gRPC 转发。
* 当前只支持在线文本转发。目标用户离线或 Redis 路由与本机会话不一致时，发送方会在 `1018` 收到错误；
  离线消息持久化仍未实现。
