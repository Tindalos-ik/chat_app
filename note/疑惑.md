###  uid 和 token 

**uid = 你是谁，token = 一张一次性通行证**，配套的 host/port = 去哪里。

* **uid**：用户唯一标识。注册时从 `user_id` 表分配，永不改变。数据库主身份、好友关系、消息路由、Redis key 全用它。
* **token**：一次性登录凭证。StatusServer 在 `GetChatServer` 时生成（纳秒时间戳 XOR 随机数转 hex），记在内存 `_tokens[uid]`；ChatServer 收到 TCP 登录时调 `Login(uid, token)` 校验。
* **host/port**：本次登录被分配到的聊天服务器地址（负载均衡的结果），客户端用它建 TCP 长连接。

**为什么必须有 token**：密码已在 HTTP 通道验证过，但 TCP 是一条全新通道，客户端只说"我是 uid 1002"谁都能冒充。token 把 HTTP 通道验证过的信任转移到 TCP 通道，且 TCP 上永远不出现密码。这就是"HTTP 验身份、TCP 验凭证"的双通道设计。

局限：token 存在 StatusServer 内存 map 里（不是 Redis），重启全失效、无 TTL、多实例不一致；生成方式属于"够用但不是密码学安全随机"。



##  Qt 信号槽为什么高并发更安全

核心是**连接类型 + 线程亲和性**：

* 跨线程连接自动用 `QueuedConnection`：调用连同参数打包成 `QMetaCallEvent` 投递到接收者线程的事件循环，**槽在接收者自己的线程串行执行，不用为接收者加锁**；
* 多线程同时 emit 同一信号时事件排队处理（TcpMgr 注释"类似排队的效果"）；
* connect 的接收者 context 销毁时连接自动断开，不会出现"回调时对象已死"的悬垂调用；
* QueuedConnection 把调用串行化，避免槽被同一信号重入打断。

注意事项：同线程默认直连，"并发安全"主要指跨线程；QueuedConnection 有参数拷贝开销；两个对象共享同一份可变数据时该加锁还得加锁。



### MySQL 该存什么、Redis 该存什么

| 数据 | 存储 | 理由 |
| --- | --- | --- |
| 账号/密码、用户资料、好友关系、好友申请、聊天记录 | MySQL | 强一致、持久、要查询 |
| 验证码、token、在线状态、未读数、离线消息暂存 | Redis | 高频、短生命周期、要过期 |

用户数据四张表（llfc1）：`user`（账号+资料）、`user_id`（uid 分配器）、`friend`（双行存储+备注）、`friend_apply`（申请状态机）。判断标准一句话：**要永久、要查询、要事务的进 MySQL；要快、要过期、高频写的进 Redis。**



###  mysqlcppconnx（X DevAPI）要点

* vcpkg 端口名是 `mysql-connector-cpp`（README 写 `mysqlcppconnx` 是笔误），CMake 链接目标 `mysqlcppconnx`，头文件 `<mysqlx/xdevapi.h>`；
* 走 X Protocol，端口 33060（经典 API 才是 3306）；
* 链式调用：`session->sql(sql).bind(...).execute().fetchOne()`，返回 `SqlResult` → `Row` → `row[i].get<T>()`；
* `Row` 有 `operator bool()`，`if (!rows)` 就是没查到；
* **列下标从 0 开始**（经典 API 从 1 开始）；
* 参数化绑定 `?` + `bind()` 防 SQL 注入；
* 出错抛异常（`std::exception`），每个数据库方法必须 try/catch。



### 聊天记录为什么用 QScrollArea + QVBoxLayout，而列表用 QListWidget

会话列表/联系人列表是"记录行"，聊天记录是"内容流"，两者本质不同，所以容器不同。

**列表为什么用 QListWidget**：每行结构统一（头像 + 名字 + 摘要/时间 + 红点），行高固定（ChatUserWid 的 sizeHint 固定 260×75）。这种"一堆结构相同的记录"正是 QListWidget 的主场——item 存数据、`setItemWidget` 塞控件，还附带选择、点击、键盘导航等列表语义。

**聊天记录为什么用 QScrollArea + QVBoxLayout**：

1. **高度动态且随宽度变化**：文字气泡换行高度不定，layout 按各 widget 的 sizeHint 自动重排，窗口拉宽后文字重新换行、高度自动重算；QListWidget 的 item 高度是插入时定死的 sizeHint，缩放后不会自动重算，要么变形要么手动遍历重算。
2. **消息流有左右对齐、分隔、分组语义**：自己发的靠右、对方靠左，穿插时间分隔条和系统提示，连续消息间距要小。QVBoxLayout 天然支持每项独立对齐和 spacing；QListWidget 里对齐要自己在行内做，分隔条变成一种特殊行，语义绕。
3. **滚动行为特殊**：新消息自动滚到底（`setSliderPosition(maximum())`）、往上翻加载旧消息时头插并保持滚动位置（offset 补偿）。QScrollArea 的 scrollbar 直接归自己管；QListWidget 是行模型，靠 `scrollToItem`，头插 + 位置补偿很别扭。
4. **没有多余语义**：QListWidget 自带选择高亮、item 角色、拖拽等列表功能，聊天气泡完全用不上。

| 维度 | 列表（会话/联系人） | 聊天消息区 |
| --- | --- | --- |
| 本质 | 结构统一、固定行高的记录 | 高度动态、混合内容的流 |
| 换行/缩放 | 不需要 | 必须自动重排 |
| 对齐语义 | 每行一个样式 | 左右气泡、时间分隔、分组 |
| 滚动 | 滚到底即可 | 自动贴底、头插补偿 |
| 合适容器 | QListWidget | QScrollArea + QVBoxLayout |

> 注意：QListWidget 底层也是一个 QAbstractScrollArea，所以问题不是"要不要滚动"，而是"item 行模型 vs widget 流"。消息量巨大（几千条以上）时的正确方案是 QListView + 自定义 delegate（真虚拟化，只绘制可见行），教学场景和中小规模用 layout 方案更直观。



### 为什么只放一个组件也要用布局

布局（layout）干的事不是"把多个组件摆开"，而是**管理组件的几何**：位置、尺寸、以及父窗口缩放时怎么跟着变。哪怕只有一个组件，这些问题照样存在。

**没有布局会怎样**：`new QScrollArea(this)` 后不管它，得到的滚动区域尺寸是 0×0（或默认值）、位置不对，父窗口拉大它也不会跟着变。要让它铺满父窗口，只能自己重写 `resizeEvent` 手动 `setGeometry(rect())`——这等于在**手写一个布局**，还得考虑边距、滚动条占位、内容变化，写几行就漏。

**有了布局会怎样**：

```cpp
QVBoxLayout* pMainLayout = new QVBoxLayout();
this->setLayout(pMainLayout);
pMainLayout->setContentsMargins(0, 0, 0, 0);
pMainLayout->addWidget(m_pScrollArea);   // 表达的是：占满父窗口、四周边距 0
```

之后父窗口变大变小、边距要不要留、将来要不要再加子控件（提示条、日期条），Qt 全部自动处理，不用写一行 resizeEvent。

| | 不用布局 | 用布局 |
| --- | --- | --- |
| 初始位置/尺寸 | 靠运气或手写 setGeometry | 自动按策略填满 |
| 父窗口缩放 | 不动，要自己写 resizeEvent | 自动重排 |
| 边距控制 | 自己加 | `setContentsMargins` 一行 |
| 以后加第二个组件 | 重写一堆几何代码 | `addWidget` 一行 |

> 替代思路：如果"反正只有一个滚动区域"，也可以让类直接继承 QScrollArea，少包一层；但"QWidget + 内部布局"是 llfc 和本项目采用的标准写法，提升到 .ui 里最灵活，不用改。



### 布局里的"弹簧"：`addWidget(new QWidget(), 100000)` 是干什么的

（ChatView 内容布局里的这行）注意：**100000 不是高度**，那个 QWidget 也不是"高组件"——它是一个 sizeHint 为 0×0 的空 widget，第二个参数是**拉伸因子（stretch factor）**，是比例/权重，不是像素。

它的作用：**把布局里的"剩余空间"全部吸走**。

**为什么需要它**：如果内容布局里只有气泡、没有弹簧，消息很少（比如 2 条）而窗口很高时，QVBoxLayout 会把多余空间按各 widget 的 sizePolicy 分掉，气泡可能被**拉高**或空间分配混乱，不再保持自然高度。有了 stretch=100000 的弹簧：

```text
窗口很高、消息很少时：
┌─────────────────────┐
│ 气泡1               │  ← 保持自然高度
│ 气泡2               │
│                     │
│   （弹簧 stretch）   │  ← 剩余空间全被它吃掉
│                     │
└─────────────────────┘
```

* **视觉上**：气泡永远挤在顶部、不被拉长，多余空间全变成弹簧占据的空白；
* **结构上**：弹簧是布局里固定的一项，所以"尾插" = 插到 `count()-1`（弹簧前面），消息永远在弹簧上方——这就是 `appendChatItem` 里 `insertWidget(count()-1, item)` 的由来；
* **消息多时**：内容超过窗口高度，弹簧自动缩到 0，滚动条出现，正常滚动；它只在"内容不满"时才撑开。

> 等价写法是 `addStretch(100000)`（加的是 spacer 而不是空 widget），效果一样；llfc 用 `addWidget(new QWidget(), 100000)`，照抄没问题。
