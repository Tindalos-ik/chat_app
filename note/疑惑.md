# 常见问题与机制解释

## UID、token、session ID 各自标识什么

| 名称 | 标识对象 | 项目中的用途 |
| --- | --- | --- |
| UID | 用户 | 用户资料、好友、消息发送者、成员关系 |
| 登录 token | 当前签发的账号凭据 | TCP 登录与资源认证 |
| session ID | 一条 TCP 会话 | 重复登录互踢、识别旧连接、条件清理 |
| host/port | 服务地址 | 指定本次连接的目标 |

StatusServer 的 `GetChatServer` 生成 token，写入 `utoken_<uid>`；ChatServer 在绑定用户前读取并比较。当前 token 没有 TTL，也没有一次性消费，同一份值还用于资源请求。凭据应保密，UID 和群号本身不提供访问权限。

## `UserMgr` 和 `CServer::_sessions` 为什么同时存在

`CServer::_sessions` 保存 `session_id → CSession`，包括尚未登录的 TCP 连接，供连接生命周期管理及心跳扫描使用。

`UserMgr` 保存 `uid → CSession`，供本机按用户推送。登录成功后建立绑定，注销时通过 `RmvUserSession(uid, session_id)` 比较连接身份再移除。旧连接的延迟回调因此不会按 UID 删除新绑定。

Redis `uip_` 标识用户所在实例，`usession_` 标识当前在线会话。跨进程无法使用本机 `shared_ptr` 查找对端，需要先定位实例，再由目标服务查询自己的 `UserMgr`。

## MySQL、Redis 和 SQLite 分别保存什么

| 存储 | 项目保存的数据 | 依赖的特性 |
| --- | --- | --- |
| MySQL | 用户、好友、会话、正式消息、回执、群管理 | 事务、约束、索引、持久查询 |
| Redis | 验证码、token、路由、计数、资料缓存、锁、通话状态 | 原子命令、共享访问、按需过期 |
| SQLite | 本账号消息缓存、会话摘要、附件状态和同步进度 | 本地事务、离线读取 |

MySQL 是正式聊天历史来源。离线消息恢复依赖数据库与同步接口，项目未使用 Redis 离线消息队列。Redis 的不同 key 有不同生命周期，不能根据验证码设置了 TTL 推断登录 token 也会过期。

## Qt 跨线程信号槽是否自动保证安全

`Qt::AutoConnection` 在发射线程与接收对象所属线程不同的情况下使用排队调用；槽在接收者线程的事件循环中执行。接收者需要可用事件循环，排队参数需要满足 Qt 的类型传递要求。

- 同线程自动连接通常直接调用，槽可在当前调用栈中执行。
- 排队传递参数涉及复制，共享指针仍可能指向同一个可变对象。
- 单线程依次执行槽不保护其他线程直接访问的共享数据。
- 接收 context 销毁会断开相应连接；lambda 捕获的其他裸指针仍需独立保证生存期。
- 手动调用槽、直接连接、嵌套事件循环或 `processEvents()` 都需额外检查并发和重入。

`TcpMgr` 的线程亲和性、socket 所属线程和信号连接方式需要一起检查，不能只根据 `emit` 判断执行线程。

## 头文件里的类型为什么必须统一定义

同一命名空间中的 `UserInfo` 应有一致定义。仅需要声明指针或引用时可以前置声明；访问字段或构造对象时需要包含完整定义。头文件中的声明与 `.cpp` 定义还必须在参数、引用、const 和命名空间上匹配。

`std::shared_ptr<UserInfo>` 按值传递可以修改对象内容；若函数需要替换调用方保存的指针，需要返回新指针或明确使用指针引用。项目共享数据类型集中在相应 `data.h` 或客户端数据头中。

Windows 与 Linux 对文件名大小写的处理不同，`#include` 应与实际文件名完全一致。

## MySQL X DevAPI 的读取规则

项目使用 `<mysqlx/xdevapi.h>` 和 `mysqlcppconnx` 链接库，通过 X Protocol 连接 `33060`。命令行 `mysql` 常用经典协议端口 `3306`。

`session.sql(...).bind(...).execute()` 执行参数化 SQL。读取结果时先判断行是否存在，再按从 0 开始的列位置和实际 SQL 类型读取。占位符适用于值，动态列名或排序字段需要限定集合。

连接池借出的 session 在事务结束前保持独占。异常路径应完成回滚和归还；SQL 文本、绑定参数和返回列发生变化时，调用方读取逻辑也需同步检查。连接库与例子见 [MySQL 连接库](MySQL连接库.md)。

## 为什么消息区使用 `QScrollArea + QVBoxLayout`

项目的 `ChatView` 使用滚动区域承载动态气泡，每条消息宽高可随文本和窗口改变；会话列表则使用具备选择与行语义的列表控件。

| 行为 | 当前消息区处理 |
| --- | --- |
| 少量消息靠上排列 | 底部伸缩项吸收剩余高度 |
| 添加新消息 | 插在最后一个伸缩项之前 |
| 顶部加载旧历史 | 批量头插，保留原始顺序 |
| 保持原阅读位置 | 按滚动条最大值增长量补偿原位置 |
| 观察顶部滚动 | 忽略程序头插、尾插造成的中间事件 |

该实现为每条消息创建 QWidget，适合其当前界面模型；大规模历史视图可研究模型/视图与 delegate 的可见项绘制，评估内存和布局成本。

## 只有一个子控件为什么也要布局

布局管理尺寸、边距、伸缩和父窗口缩放关系。一个 `QScrollArea` 放入父控件布局后，父窗口变化时可自动调整几何；纯粹设置 parent 只建立对象关系，不会表达填满可用空间的规则。

`ChatView` 的外层布局使用零边距，让滚动区域占据可用区域；内容控件再用垂直布局管理消息。对象父子关系、布局关系和绘制样式分别解决生命周期、几何和外观问题。

## `addWidget(new QWidget(), 100000)` 的数字含义

第二个参数是布局伸缩因子。项目把空 QWidget 放在内容布局尾部，用较高伸缩权重承接剩余空间；它不表示十万像素高。

消息使用 `insertWidget(count()-1, item)` 放在伸缩项之前。清空历史时保留该项，否则少量消息可能重新分配多余高度。`addStretch()` 也是表达可伸缩空白的 Qt API，维护现有实现时需同时考虑插入和清空逻辑。

## UI 发送信号与网络发送有什么关系

`MessageTextEdit::send()` 表达用户按下发送快捷键；`ChatDialog::on_send_btn_clicked()` 读取内容、确定会话并组织业务请求；`TcpMgr::sig_send_data()` 把协议 ID 与 JSON 交给统一发送槽。

`TcpMgr` 持有 `QTcpSocket`，统一写入两个大端 16 位头字段：协议 ID 和 JSON 字节长度。`socket.write()` 接受字节只说明进入本地发送路径；服务端保存与对端展示分别需要业务响应和 ACK。

文本请求的 `textArray` 是一个 JSON 数组，每个元素有自己的 `content/msgid`。外层保存请求路由及会话字段，服务端逐条处理，客户端按元素 ID 关联结果。图片与文件使用各自资源上传和发送协议，详见 [图片传输](图片传输.md)、[文件传输](文件传输.md)。

## UUID 能否保证重发不重复

客户端生成 UUID 只提供稳定关联。服务端要保证同一次业务只提交一次，还需要持久唯一约束、原子查重或操作结果记录。当前文本消息重发相同 UUID 仍可能新增正式消息；本地按 `message_id` 去重只处理正式记录的重复接收。

群管理的 `operation_id` 有独立业务重放规则，应按原业务输入重放并返回正式结果，不能直接套用文本消息 UUID 的处理方式。

## Git SSH 连接失败如何定位

先确认报错发生在网络连接、主机密钥、SSH 身份还是仓库授权阶段。`Connection closed ... port 22` 需要检查 SSH 网络路径；`Permission denied (publickey)` 需要检查密钥与账号；仓库权限错误需要检查远程地址和授权。

代理、防火墙与 SSH 配置影响实际连接路径。切换协议前检查目标服务是否可达，避免把网络错误与仓库权限混在一起。
