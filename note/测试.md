# 自动化测试

本项目 C++ 测试由 GoogleTest 编写、CTest 启动，源码和目标定义位于 tests/，覆盖 TCP、好友事务、私聊消息、群事务权限、SQLite 缓存与连接容量。真实服务 smoke 与数据库单元/集成测试分开记录，不能把数据层通过当成跨服/UI通过。

## 构建与选择运行

根目录 `CMakeLists.txt` 已通过 `add_subdirectory(tests)` 接入测试子目录；`include(CTest)` 默认启用 `BUILD_TESTING`。在仓库根目录配置并默认构建一次，所有测试目标都会一起编译：

```powershell
cmake --preset windows-vcpkg
cmake --build --preset debug
```

当前桌面 Qt 使用 MinGW，而根目录服务与测试使用 MSVC，二者 ABI 不兼容。根 CMake 会读取桌面端 `CMakeCache.txt` 中的 Qt、编译器和 Ninja 路径，并把 SQLite 测试作为根默认构建中的一个目标，在独立 Ninja 子构建中编译；这个子构建由根目录 `cmake --build` 自动调用，不需要手动编译。它还会用 vcpkg 的 GoogleTest 源码重新编译匹配 MinGW 的 GoogleTest。CTest 运行 SQLite 用例时，再由根目录注册的入口转发到该子构建。

从仓库根目录运行交互脚本，可以逐项选择需要运行的测试：

```powershell
.\run_tests.ps1
```

每项输入 `y` 表示运行，直接回车或输入 `n` 表示跳过。也可以通过参数直接选择，不显示提示：

```powershell
.\run_tests.ps1 -Tests tcp,friend,message,sqlite
.\run_tests.ps1 -Tests capacity
.\run_tests.ps1 -Configuration Release -Tests tcp,sqlite
```

可选名称为 `tcp`、`friend`、`message`、`sqlite`、`capacity`。脚本只用 CTest 运行所选用例，不会重新配置 CMake 或重新编译。若在交互菜单中选中多个测试，脚本会合并普通 CTest 用例运行；容量测试单独运行。

## 1. TCP 半包、粘包与帧解析

**测试什么**

检查服务端协议帧解析能否跨 TCP 读取边界恢复帧：

- 包头和包体分多段到达时，未收完整之前不产生帧，收完整后消息 ID 和包体正确。
- 一次输入含有多个连续帧时，所有帧都被解析且顺序不变；多帧流以不同大小分块输入时也能持续解析。
- 消息 ID 为 0 或大于 `MAX_LENGTH`、包体长度为 0 或大于 `MAX_LENGTH` 时拒绝该帧。
- 有效帧后紧接非法头部时，解析报告错误的同时保留之前已经完整解析出的帧。

**怎么测试**

`tests/tcp_stream_test.cpp` 直接调用生产代码的 `chat_protocol::TcpFrameParser::Feed()`，构造协议头和包体后，把字节流按指定位置切分并检查返回帧。该测试不启动 TCP 服务或 socket，可重复、确定地覆盖六种输入情况。

```powershell
.\run_tests.ps1 -Tests tcp
```

**修改了什么代码**

- 新增 `ChatServer1/include/TcpFrameParser.h`，将包头校验、残留字节保存和完整帧提取封装为增量解析器。
- 修改 `ChatServer1/include/CSession.h`、`ChatServer1/src/CSession.cpp`：`CSession` 从分别读满包头和包体，改为 `ReadSome()` 接收任意字节块、调用解析器，再由 `HandleFrame()` 逐帧走原有心跳或业务处理路径。
- 新增 `tests/tcp_stream_test.cpp`，并在 `tests/CMakeLists.txt` 注册 TCP 单元测试目标。

原来的异步读满逻辑也能处理半包。本次改动把解析边界从 socket 回调中分离出来，使生产解析代码可以直接接受单元测试输入。

## 2. 好友申请与认证事务

**测试什么**

验证好友申请读取、好友认证和事务原子性：

- 同一用户对重复提交申请时，申请记录保持一条且申请备注更新；接收方能读到待处理申请。
- 认证后申请状态变为已处理，双方好友关系及各自备注正确，并只创建一个私聊会话和一条初始认证消息。
- 重复认证时不重复插入好友关系、私聊或初始消息。
- 初始消息插入失败时，好友关系、会话和消息一起回滚，申请仍保持待处理。

**怎么测试**

`tests/friend_transaction_test.cpp` 连接显式指定的隔离 MySQL schema，分配临时 UID 并创建测试用户，然后调用生产 `MysqlMgr::AddFriendApply()`、`GetFriendApplyInfo()` 和 `AddFriend()`。回滚场景会创建一个临时 MySQL trigger，使测试用户的初始消息插入失败；用例检查事务结果后移除 trigger 并清理自己创建的数据。

运行前需要在隔离 schema 中部署 `user`、`friend`、`friend_apply`、`chat_thread`、`private_chat` 和 `chat_message` 表，所有相关表应使用 InnoDB。schema 名必须包含 `test`，不能使用 `chat_app_db`。设置以下变量后运行：

```powershell
$env:CHAT_FRIEND_TEST_CONFIRM_ISOLATED = 'YES'
$env:CHAT_FRIEND_TEST_MYSQL_HOST = '127.0.0.1'
$env:CHAT_FRIEND_TEST_MYSQL_PORT = '33060'
$env:CHAT_FRIEND_TEST_MYSQL_USER = 'test_user'
$env:CHAT_FRIEND_TEST_MYSQL_PASSWORD = '123456'
$env:CHAT_FRIEND_TEST_MYSQL_SCHEMA = 'chat_app_test_local'
.\run_tests.ps1 -Tests friend
```

缺少任一配置时用例会标记为 `Skipped`，不会连接数据库。MySQL 用户还需要有创建和删除测试 trigger 的权限。

**修改了什么代码**

- 新增 `tests/friend_transaction_test.cpp`，测试真实好友数据层接口和数据库提交结果。
- `tests/CMakeLists.txt` 新增 `chat_mysql_test_support` 测试依赖库，链接生产 `MysqlMgr`、`ConfigMgr`、`RedisMgr`、`DistLock` 实现，以及 MySQL Connector、Redis++ 和 GoogleTest。
- 本次没有改动生产好友申请、好友认证或其 SQL schema；测试验证的是现有 `MysqlMgr` 行为。

## 3. 消息重试、离线同步与回执

**测试什么**

- 接收方先按 `message_id` 拉取一页，离线期间服务端继续保存新消息；接收方从上次游标继续分页，最终恢复全部消息且没有遗漏，游标单调向前。
- 重试相同文本请求和客户端消息 ID 后，检查当前服务端的实际结果。现状是新增另一条 `chat_message`，获得新的 `message_id`；本测试记录此行为，不表示重试已去重。
- 验证送达显示状态和已读游标写入后可从历史记录读回；重复提交同一回执不会产生新的状态变更。

**怎么测试**

`tests/message_retry_offline_sync_test.cpp` 使用配置好的测试 schema 调用真实 `MysqlMgr` 消息保存、历史分页、显示回执和已读接口。离线场景通过在两次分页读取之间插入消息来模拟接收方掉线期间的服务端状态；不启动 ChatServer，也不测试 Redis 在线路由。

运行前创建名称以 `chat_app_test_` 开头的隔离 schema。仓库提供 `sql/chat_app_test_local.sql`，包含 `chat_app_test_local` 的完整 DDL，从 `CREATE DATABASE`、`USE` 到九张表。执行方式如下；MySQL 命令行客户端默认使用传统协议端口 `3306`，项目服务和测试连接使用 X DevAPI 端口 `33060`：

```powershell
$ddl = Get-Content .\sql\chat_app_test_local.sql -Raw
mysql --default-character-set=utf8mb4 --protocol=tcp -h 127.0.0.1 -P 3306 -u root -p -e $ddl
```

该脚本的表结构应与 `sql/create_tables.sql` 保持一致；结构更新时需同步更新两份脚本。它已包含消息、回执、图片和文件字段；新测试库不需要再导入 `sql/chat_message_storage.sql`。脚本不会删除已有 schema 或数据；已有旧版 `chat_message` 表应按数据库设计笔记中的步骤执行迁移。测试从 CTest 工作目录 `build/tests/config.ini` 的 `[Mysql]` 段读取连接配置，同时要求环境变量与文件中的 host、port、user、schema 一致：

```powershell
$env:CHAT_MESSAGE_TEST_DB_HOST = '127.0.0.1'
$env:CHAT_MESSAGE_TEST_DB_PORT = '33060'
$env:CHAT_MESSAGE_TEST_DB_USER = 'test_user'
$env:CHAT_MESSAGE_TEST_DB_SCHEMA = 'chat_app_test_local'
.\run_tests.ps1 -Tests message
```

`config.ini` 还需要配置 `passwd`。缺少配置、schema 前缀不正确或文件与环境变量不一致时，用例会跳过。测试生成唯一 UID 对，并清理对应的消息、私聊和会话数据。

**修改了什么代码**

- 新增 `tests/message_retry_offline_sync_test.cpp`，通过生产消息数据层实现验证离线历史、分页游标、重试结果和回执持久化。
- 该目标与好友事务测试共用 `chat_mysql_test_support`，在 `tests/CMakeLists.txt` 中注册为 MySQL 集成测试。
- 本次没有更改生产消息保存、游标查询、回执逻辑或数据库 schema。当前重试重复写入是已观测到的产品行为。

## 4. 客户端 SQLite 缓存

**测试什么**

- 两个 UID 使用不同数据库文件；相同会话 ID、消息 ID 写入不同账号后，缓存和同步游标不串号。
- 重复写入会话和相同 `message_id` 时更新已有记录；较小游标不能覆盖较大游标。
- 一批消息中包含无效会话时，事务整体回滚，先前有效消息和游标都不落库。
- 会话已读数、消息已读状态和投递状态正确推进；较旧同步数据不能撤销已读或降低状态。
- 关闭后重开数据库，会话摘要、消息、已读状态及同步游标仍可恢复。

**怎么测试**

`tests/local_chat_storage_test.cpp` 创建 `QCoreApplication` 和 `QTemporaryDir`，实例化真实 `LocalChatStorageMgr`，通过临时目录初始化 SQLite。每次打开数据库后都检查数据库实际路径位于临时目录内；因此测试不读写用户的真实应用缓存。运行需要 Qt 6.5+ Core、Sql、Widgets 及可用的 `QSQLITE` 驱动。Windows 上若根目录编译器与桌面 Qt 编译器不同，测试会复用桌面构建缓存并使用独立子构建，避免把 MinGW Qt 链接进 MSVC 目标：

```powershell
.\run_tests.ps1 -Tests sqlite
```

**修改了什么代码**

- 新增 `tests/local_chat_storage_test.cpp`，包含账号隔离、事务回滚、状态单调更新和关闭重开恢复用例。
- 修改 `chat_app desktop/localchatstoragemgr.h/.cpp`：`Initialize()` 增加可选的绝对路径参数 `cacheRoot`。测试传入临时路径；正常客户端不传参数时仍使用 `QStandardPaths::AppLocalDataLocation`。重复初始化时会比较 UID 和最终数据库路径，根目录变化也会关闭旧连接并打开目标文件。
- `tests/CMakeLists.txt` 增加 Qt 6.5+ 测试目标；Windows 上检测到根目录 MSVC 与桌面 MinGW Qt 不匹配时，改用桌面 `CMakeCache.txt` 配置独立构建和 CTest 转发。
- 新增 `tests/sqlite/CMakeLists.txt` 与 `tests/sqlite/run_nested_ctest.cmake`，在匹配的 Qt/MinGW 环境编译 SQLite 测试和 GoogleTest。

## 5. 连接容量

**测试什么**

统计单台客户端可同时连接到目标 ChatServer 的 TCP 长连接数量，并记录第一次连接失败时的 socket 错误。它测的是被测环境下客户端或服务端先遇到的资源限制，不是服务端固定容量保证。

**怎么测试**

`tests/connection_capacity_test.cpp` 在 Windows 上对配置的端口逐轮建立 TCP 连接并保留 socket；所有连接建立完成或达到上限后保持一段时间，再关闭连接。默认目标是 `127.0.0.1:8090,8091`，每台至少要求 100 条，最多尝试 20000 条，保持 1000 毫秒。若所有端口都因 `WSAECONNREFUSED` 拒绝连接，用例会跳过；非 Windows 平台也会跳过。连接关闭时使用 RST，减少测试后残留的 `TIME_WAIT`。

先启动 ChatServer1 和 ChatServer2，再选择运行：

```powershell
.\run_tests.ps1 -Tests capacity
```

可用 `CHAT_CONNECTION_HOST`、`CHAT_CONNECTION_PORTS`、`CHAT_CONNECTION_MIN`、`CHAT_CONNECTION_MAX`、`CHAT_CONNECTION_HOLD_MS` 调整主机、端口、连接下限、探测上限和保持时间。单客户端可能先遇到本地动态端口或 socket 缓冲限制；输出的错误码用于区分客户端耗尽、服务拒绝和超时。容量结果受操作系统及测试机限制，超过一次测试的探测上限需要调高上限或从多台客户端继续测。

**修改了什么代码**

- `tests/connection_capacity_test.cpp` 是仓库原有容量测试，本轮没有修改其探测代码。
- `tests/CMakeLists.txt` 保留该目标并标记为 `capacity`，交互脚本将其单独询问和运行。容量测试不需要 MySQL 或 Redis。
