# 单元测试 / 集成测试总结

> 本文记录仓库 `tests/` 目录下的测试现状、运行方式、实测结果，以及后续补测计划。

## 1. 现状：框架有了，但还不是真正的"单元测试全覆盖"

当前 `tests/` 目录只有一个测试目标：

| 文件 | 类型 | 作用 |
| --- | --- | --- |
| `tests/connection_capacity_test.cpp` | GoogleTest + CTest 集成测试 | 对真实 ChatServer1/2 建立并保持 TCP 连接，探测连接容量 |
| `tests/CMakeLists.txt` | CMake | 编译测试目标并把用例注册到 CTest（label: `capacity`） |

严格说它属于**集成测试**，不是纯内存单元测试：需要 MySQL、Redis、两个 ChatServer 都启动，测试才会真正建连。

目前没有针对以下模块的独立单元测试：

- `CSession` 的半包/粘包/非法包头解析；
- `LogicSystem` 的登录校验、消息路由、好友申请逻辑；
- `MysqlMgr` 的事务与幂等；
- `RedisMgr` 的 key 操作；
- Qt 客户端 `TcpMgr` 的收包解析。

所以面试或文档中建议这样表述：项目使用 GoogleTest/CTest，并先做了一个最有说服力的容量集成测试；业务模块的单元测试是后续要补的。

## 2. 连接容量测试做了什么

测试行为（已修改为"逐步逼近上限"版本）：

1. 依次对 `CHAT_CONNECTION_PORTS` 指定的每台 ChatServer 建立并**保持**空闲 TCP 连接。
2. 一直加到第一次建连失败，或每台都达到 `CHAT_CONNECTION_MAX`。
3. 结束后打印每台的成功连接数和第一个 socket 错误码，再统一关闭连接。
4. 关闭时使用 `SO_LINGER=0` 主动发 RST，避免测试后留下大量 `TIME_WAIT` 占用本地动态端口。
5. 如果所有目标端口都拒绝连接，测试判定"服务没启动"并跳过，不会误报为容量不足。

## 3. 运行方式

前置条件：

- MySQL、Redis 已启动；
- ChatServer1/2 已启动并监听 `8090/8091`；
- 已构建项目和测试目标。

构建：

```powershell
cmake --preset windows-vcpkg
cmake --build --preset debug --target connection_capacity_test
```

运行：

```powershell
ctest --test-dir build -L capacity --output-on-failure
```

或直接运行可执行文件：

```powershell
.\build\tests\Debug\connection_capacity_test.exe
```

环境变量：

| 环境变量 | 默认值 | 含义 |
| --- | ---: | --- |
| `CHAT_CONNECTION_HOST` | `127.0.0.1` | 被测服务主机 |
| `CHAT_CONNECTION_PORTS` | `8090,8091` | 被测端口列表 |
| `CHAT_CONNECTION_MIN` | `100` | 每台至少达到的连接数 |
| `CHAT_CONNECTION_MAX` | `20000` | 每台最多探测的连接数 |
| `CHAT_CONNECTION_HOLD_MS` | `1000` | 全部建完后保持连接的毫秒数 |

只压 8090 一台：

```powershell
$env:CHAT_CONNECTION_PORTS = '8090'
ctest --test-dir build -L capacity --output-on-failure
```

## 4. 实测结果（2026-09-09，本机）

环境：Windows、ChatServer1:8090 与 ChatServer2:8091 同时运行，本机 TCP 动态端口范围默认 `49152~65535`（共 16384 个）。

| 场景 | 结果 | 停止原因 |
| --- | --- | --- |
| 双台并行，上限 20000（第 1 次） | 8090: 8068、8091: 8067 | 客户端 `WSAENOBUFS(10055)` |
| 双台并行，上限 20000（复跑） | 8090: 8071、8091: 8071 | 客户端 `WSAENOBUFS(10055)` |
| 只压 8090，上限 20000 | 8090: 16057 | 客户端 `WSAENOBUFS(10055)` |

结论：

1. **1000 不是 ChatServer 的连接上限**，它只是旧测试的默认探测值。
2. ChatServer 代码里没有最大连接数常量，`CServer` 只把连接放进 `_sessions`，不会主动拒绝。
3. 单机单客户端并行压两台时合计约 16000 条、只压一台约 16000 条后，先撞上**客户端本地动态端口/缓冲**限制，而不是服务端拒绝（`WSAECONNREFUSED` 未出现）。
4. 测试结束后两台 ChatServer 句柄数回到基线，`netstat` 无 TIME_WAIT 残留，可以连续复跑。

错误码含义：

| 错误 | 含义 |
| --- | --- |
| `WSAEADDRINUSE` / `WSAEADDRNOTAVAIL` | 客户端本地端口耗尽 |
| `WSAENOBUFS` / `WSAEMFILE` | 进程句柄、内存或缓冲资源不足 |
| `WSAECONNREFUSED` | 服务未监听 / backlog 满 / 防火墙拒绝 |
| `WSAETIMEDOUT` | 建连超时 |

为什么有连接上限？windows默认的动态端口是1024-65535，每个tcp长连接都会占用一个端口，即使连接关闭，端口也需要一段时间才可以复用

## 5. 为什么给不出固定"连接上限"

容量取决于多个因素，不是服务端一个常量决定的：

1. 客户端侧：单网卡动态端口数（Windows 默认约 16384）、进程 socket 句柄数；
2. 服务端侧：socket 句柄、每个 `CSession` 的内存（`_data`、MsgNode、队列等）、监听 backlog、网络栈；
3. 业务侧：是否登录、是否收发消息、Redis/MySQL 连接池大小、单线程业务队列吞吐；
4. 系统侧：TCP TIME_WAIT 回收、非分页缓冲池、杀软/防火墙。

因此准确说法是："当前环境下，单客户端实测至少能建立约 16000 条空闲 TCP 连接；要继续测服务端真实上限，需要多客户端/多源 IP 同时压。"
